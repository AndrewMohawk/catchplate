# Data Plane Candidates

The production track is the Rust data plane. It owns policy evaluation, absolute-form forwarding, explicit CONNECT MITM, upstream TLS validation, scoped credential injection, response validation/projection, bounded credentialless and redacting stream modes, one-use shared JIT grants, and shared quotas. The Python mitmproxy transport is credentialless development compatibility only and rejects credential-bearing routes before secret, JIT, quota, reservation, or provider work. Rust is not an arbitrary streaming mutation proxy: each mutable format needs a dedicated bounded validator, credential-bearing opaque responses are forbidden, and credential-bearing mutating requests must be buffered and validated before release.

## Rust Decision Gate

Location: `data-plane/decision-gate-rs`.

The gate loads `/data/policy-bundle.json`, obtains the policy signing trust root from the control-plane attestation, verifies the quote and Ed25519 bundle, and checks a persistent policy high-water record before compiling principals and routes into memory. Every production control-plane writer flocks the same shared policy-volume directory inode beneath root-controlled ancestry. Publication binds the full candidate, predecessor, and signed-bundle digests under that lock and distinguishes pending, committed, and database-commit-ambiguous outcomes. The same high-water check runs on hot reload, so stale signed sequences and rollback epochs are rejected across restarts while the last good snapshot remains active. The shared volume namespace and persistent control-plane/gate high-water histories require protected storage; coordinated rollback remains an external deployment boundary. Proxy forwarding and public attestation use port `9090`. Authenticated management calls use a separate `9091` listener that production does not publish. `SERVERWARE_POLICY_SIGNING_PUBLIC_KEY` remains only a test fallback; Docker uses the attested trust root.

The decision API covers:

- principal checks from source CIDR, trusted headers, and hashed `Proxy-Authorization` bearer tokens with token expiry and token-specific source CIDR binding;
- raw HTTP `CONNECT` preflight that denies missing principal identity, missing/bad/expired/wrong-source proxy tokens, unknown hosts, and unknown ports before leaf-certificate generation;
- explicit CONNECT TLS interception with cached dynamic leaf certificates signed by the verifier-installed data-plane CA handoff, including sequential keep-alive requests inside one intercepted tunnel;
- absolute-form HTTP proxy forwarding for policy-allowed `http://` and `https://` targets, with proxy-auth and Serverware-only identity headers stripped before upstream forwarding;
- upstream hostname and WebPKI validation, with `SERVERWARE_UPSTREAM_CA_BUNDLE` adding private roots without disabling the platform roots; this is not route-level leaf/SPKI pinning;
- host, port, method, and path-template route matching;
- request-only adapter checks for `generic.rest`, `gmail.v1`, `x.v2`, and `npm.registry`, including bounded generic required request headers that are distinct from principal identity headers;
- shared route constraints for operation allow/deny lists, rolling fixed-window and UTC calendar-window credential quotas, query lookback windows, query numeric caps, JSON body rules, and JSON response date-window validation;
- authenticated shared quota consumption through `POST /api/data-plane/rate-limits/consume` when a `rateLimit` constraint uses `store: "shared"`, so rolling and calendar credential budgets are atomic across Rust data-plane replicas. `windowSeconds` remains first-use-anchored; `calendarWindow` uses half-open `utcDay`, Monday-based `utcIsoWeek`, or `utcMonth` boundaries. A UTC day resets at 00:00 UTC, and an undispatched pre-boundary reservation expires instead of crossing into the next bucket;
- Gmail recent-query rewrite planning and unproven direct-message read denial;
- X read/write classification and credential app metadata binding;
- npm publish/dist-tag classification, required field extraction, and JIT-required decisions;
- canonical request and operation digests bound to policy hash, credential ref, and credential version;
- authenticated, non-authoritative local JIT grant cache through `POST /v1/grants` for dev fallback, addressed by principal, route, credential ref/version, policy hash, request digest, and operation digest;
- atomic one-use grant consumption through the shared control-plane grant endpoint before returning a credential injection plan when `SERVERWARE_CONTROL_PLANE_GRANT_CONSUME_URL` is configured;
- control-plane approval publish integration, with shared-consume digest parity tested against a real proxy-created npm approval;
- optional `SERVERWARE_EXPECTED_CONTROL_PLANE_QUOTE_KEY_ID` and `SERVERWARE_EXPECTED_POLICY_SIGNING_KEY_ID` startup pins so a replaced control-plane quote signer or policy signing key is rejected before any policy snapshot becomes active;
- signed policy hot reload from a background watcher, with no request-path filesystem calls and fail-closed last-good retention for invalid bundles;
- separate recipient-bound generation and secret caches for one exact principal/route/credential/policy scope: cold scopes perform no prefetch or background work, generation checks singleflight on demand, and only successful authenticated request scopes stay hot for bounded renewal;
- stale JIT grant invalidation when a fresh scoped lease rotates or removes the selected credential version;
- decision-time rejection for missing, deleted, or expired credential leases;
- caller-supplied `credentialVersions` ignored in favor of the authenticated lease cache;
- credential injection from recipient-bound leases during forwarding, while decision responses still carry injection plans by credential reference only;
- status-specific response contracts: `2xx` uses the success profile, `4xx`/`5xx` requires an explicit bounded error profile, redirects are blocked, and malformed or oversized bodies fail closed;
- structured response projection for Gmail, generic REST, X, and npm, including Gmail date proof and message-header filtering plus policy `allowedFields` redaction;
- mandatory closed provider request profiles for Gmail, X, and npm, with exact admitted headers, query keys, media types, and body limits and no legacy defaults; violations are rejected before credential leases, JIT/grants, quotas, release authorization, or upstream contact, while a bodyless request remains bodyless when it carries a syntactically valid `Content-Type`;
- signed optional `routes[].match.resolvedCidrs`: omission is public-only, explicit CIDRs are compiler-canonicalized, and metadata overlaps remain forbidden. The Rust transport uses four bounded resolver workers, a 256-job queue, a two-second timeout, a 32-answer maximum, whole-answer-set validation, deterministic single-address selection, original-host SNI/certificate checks over a pinned socket, and a 256-entry pinned-client cache. It performs no alternate-address retry or re-resolution, reuses the prepared client for Gmail metadata children, and fails before credential/JIT/quota side effects;
- paired `npm.publish` success contracts in Rust, plus credentialless Python semantic-parity checks: compatible registries retain buffered package/version `responseBinding` plus required `published: true`, while exact `registry.npmjs.org` routes require the fixed `npm-public-registry-receipt-v1` contract, accept only `200`/`201` with one strict `application/json` header and an object body, permit `{}`, reject any present `ok`/`published` value other than boolean `true`, and strip every untrusted identity claim before release; failures synthesize `502` before provider bytes are released;
- policy-selected safe response headers limited to `Cache-Control`, `Content-Language`, `ETag`, `Last-Modified`, `Retry-After`, and `WWW-Authenticate`; state-bearing, redirect, hop-by-hop, encoding, and upstream framing headers are stripped;
- credential-bearing `response.mode: "any"`, non-redacting `response.mode: "stream"`, and credential-bearing mutating request streams rejected at policy admission;
- buffered response digest headers plus nonce-requested runtime proof headers; the GET-only external proof client emits `serverware.proxyResponseProof/v3`, binding the collector-observed principal and independently matched route, the historical release identity, raw upstream status/body/policy-header digests, projected response bytes and headers, policy, runtime, executable, release, instance, and TLS exporter. Rust requests and verifies a nonce-bound `serverware.responseSignature/v3` control-plane `/dispatch` response with the attested control-plane response key; v3 binds digests of the exact query bytes and canonical end-to-end response-header multimap without copying raw query, cookie, or header values into proof headers. It then embeds the exact signed body, canonical header-digest preimage, and proof headers as `serverware.controlPlaneAuthorizationReceipt/v1`; no post-produced receipt file is required. The historical authority time is the control plane's signed `dispatchStartedAtEpochMs`, and the inline statement makes no current authorization, completion, forwarding, or downstream-delivery claim;
- an optional development `serverware-custody-runtime` with a 256 KiB-capped UDS protocol whose exact ordered hello capability set is `hello/v1`, `responseProof.sign/v2`, `streamingResponseProof.sign/v1`, `responseObservationProof.reserve/v1`, and `responseObservationProof.sign/v1`; the gate rejects any capability or runtime-limit substitution. Among application processes only custody holds the proof key. Every signing operation accepts a strict typed canonical statement with unknown fields denied. Streaming signing validates `serverware.streamingResponseStatement/v1`; observation reservation durably binds a fresh structured nonce to the request aggregate before upstream contact, and observation signing validates `serverware.responseObservationStatement/v1`, including its closed response-path/upstream-attempt state and nullable pre-dispatch authorization evidence. Final signing durably consumes that reservation into one statement commitment while separately claiming the signed authorization attempt, so neither the nonce nor the attempt can be rebound to a different final statement across a clean restart. Authorized statements embed the signed control-plane authorization receipt and its digest, control-plane runtime-manifest digest as distinct from the gate runtime digest, policy and provenance, and complete canonical release binding including the operation-context digest and quota window kinds. Buffered, streaming, and observation operations share one checksummed, fsynced, 65,536-entry durable one-attempt/one-statement ledger through dispatch expiry, so an attempt accepted by one operation cannot be rebound through another. Exact retries are idempotent; substitution is rejected across clean restarts. Startup requires preinitialized owner-only state and rejects missing, corrupt, inconsistent, symlinked, linked, or incorrectly owned state. The gate authenticates the configured peer UID, pins custody's boot/proof key/control-plane response-key identity, repeats a full hello every second, and fails health after six seconds of stale or invalid identity as well as on signing or full-proof assembly failure. Counted operation-sequenced health transitions preserve concurrent sends, while a phase-fair ticketed dispatch authority holds send permits through upstream execution and gives policy and credential mutations FIFO-exclusive phases. After every wait, the final boundary revalidates the exact policy snapshot, attested trust, credential generation, secret fingerprint, metadata, and lease expiry. Changed boot or key identity requires a coordinated gate restart. The active control-plane private response key is not mounted into gate or custody; their read-only self-published public material is a consistency check, not an independent trust root. Custody authorizes the gate's statement but does not independently observe upstream bytes, the TLS exporter, or gate runtime facts. A crash between binding and manifest publication can require operator recovery, host snapshot rollback is not detectable without TEE-sealed monotonic state or an external witness, and blocking host networking cannot make an absolute deadline atomic with the kernel write after process suspension. UDS reports `hardware_proof:false`; it is local process separation, not hardware-backed or enclave custody;

## Credential Lease Operation

Set `SERVERWARE_CONTROL_PLANE_CREDENTIAL_LEASE_URL` to `POST /api/data-plane/credential-leases` and provide the dedicated high-entropy `SERVERWARE_DATA_PLANE_CREDENTIAL_LEASE_TOKEN` or `_FILE` setting. Each `serverware.credentialLeaseRequest/v3` names one closed purpose plus one principal, route, and credential and includes a fresh ephemeral X25519 key, one-use nonce, active policy hash, measured executable digest, and requested five-second TTL. `generationMetadata` forbids dispatch bindings and secret material. `dispatchSecret` requires the exact expected generation and metadata digest and, for JIT, an exact live atomic release reservation. The control plane verifies that assignment against the active signed policy. Unknown fields, scope mismatches, nonce replay, wrong key IDs, stale policy, wrong binary digest, and purpose substitution fail closed.

The response uses `serverware.credentialLeaseEnvelope/v2` and `X25519-HKDF-SHA256-AES-256-GCM`; its encrypted plaintext is `serverware.credentialLeaseSet/v3`. AES-GCM AAD and the decrypted set repeat purpose, recipient key/nonce, policy, executable, principal, route, credential, issue-time, expiry, generation, metadata digest, and applicable release bindings. Rust first verifies the canonical HTTP response statement with the Ed25519 key obtained from attestation, then authenticates/decrypts, rejects unknown fields, and rechecks every binding. Cache commits are monotonic: lower credential versions and same-version secret or metadata changes are rejected, while a higher version atomically replaces only the same scoped entry.

Docker sets `SERVERWARE_CREDENTIAL_LEASE_POLL_SECONDS=0.25`. Cold policy scopes are neither prefetched nor background-refreshed. Real requests and authorized previews synchronously singleflight missing or expired secret-free generation metadata, but previews do not mark a scope hot. Only successful authenticated non-preview use keeps the exact scope hot for 30 seconds. A bounded worker pool refreshes hot generation entries within one second of expiry and may renew non-JIT hot secrets; JIT background work never requests `dispatchSecret`. The caches, work queue, and worker count are bounded and exposed in health/attestation state. Failed renewal preserves a still-valid entry only until expiry, expired or invalid secrets are pruned and zeroized, final forwarding rechecks current policy/generation/secret/expiry, and policy reload prunes scopes absent from the new snapshot.

Development Docker uses a software recipient and therefore does not protect process memory from host root. Production requires the recipient-attestation generator and control-plane verifier command pair; their v2 statements bind the recipient plus principal, route, and credential. This command contract is only an integration point. Real completion still requires NSM evidence binding the recipient key and scope to production PCRs, KMS `CiphertextForRecipient` delivered into the enclave, in-enclave unwrap/injection, and parent-host observation proving plaintext is not visible.

The active Python, Rust, and Docker paths do not use `/data/credential-generations.json` or plaintext `/data/credential-leases.json`; startup removes those legacy names and `.tmp` variants. Old snapshots and backups cannot be sanitized by startup cleanup, so rotate every credential that an older release published through those files.

### Production bootstrap contract

The current static launcher consumes the closed `serverware.productionReadinessLaunch/v3` manifest. It sends `serverware.launchAuthorizationRequest/v2`, verifies `serverware.launchAuthorization/v2`, and emits `serverware.bootstrapReceipt/v3` on sealed descriptor `198`. Release orchestration requires a fresh successful systemd invocation receipt and rejects condition-skipped, stale, or nonzero units. The launcher projects authorization expiry once onto Linux `CLOCK_BOOTTIME`; the child completes setup and waits behind an exact one-byte plus EOF barrier until the parent validates the process group and deadline. Expiry `SIGKILL`s the process group, leader, and adopted descendants. An earlier nonzero phase status is terminal and cannot be erased by a later phase. This entire path is `trusted-host-readiness` under `trusted-host-wall-clock`; host preflight and the readiness runner reject final mode. Production fixes `stateDirectory` at `/var/lib/serverware/production-proof` and fixes the v1 attempt journal and lock at `launch-authorization-attempt.v1.json` and `launch-authorization-attempt.v1.lock` beneath it. The generator and launcher reject alternate production paths.

The v3 manifest binds two external rollback systems. `nonceRollbackAssurance` pins the verifier-state service and signed store assurance. `authorization.monotonicWitness` pins an independently administered monotonic witness, a separately signed witness-store-assurance document, both identities and administrative domains, and the exact witness/store trust keys and digests. Registry v2 and ledger schema v7 remain necessary but are not sufficient; coordinated local rollback without the external witness is rejected. The manifest also binds a canonical `serverware.productionLaunchGlobalRoleRegistry/v1`, its independently pinned file digest, ten pairwise-distinct native-contract SPKIs, and ten roles explicitly outside the native claim.

Ledger v7 does not accept an in-place assumption that v5/v6 state is equivalent. Operators must migrate old ledgers offline while preserving witness high-water, sticky revocation, and prepared-operation state, or deliberately reinitialize and reprovision them. Regenerate the v3 manifest and global-role registry and digest pins, then drain or explicitly migrate every nonterminal old-contract operation before enabling v7.

The host output is the closed [completion proof v6](../schemas/completion-proof.v6.schema.json), serialized as exact compact canonical JSON followed by one LF, with `actionAuthorization:null` and `okForAction:false`. Final authority belongs only to the independent Manifest-v6 public Nitro verifier, which emits the closed [release completion verification v1](../schemas/release-completion-verification.v1.schema.json) after fully validating and recomputing the nested canonical v6 core rather than trusting a shallow digest or alternate serialization. Public Nitro live-result signatures use the exact domain `serverware.publicNitroLiveVerificationResultEnvelope/v1\x00signatureAlgorithm=Ed25519\x00`; integers are limited to `0..9223372036854775807`; providers match `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`; terminal state is `responsePending` with no downstream delivery claim; the verifier-state endpoint is literal IPv4 under one total deadline; and terminal pruning/capacity/no-replace publication uses one directory-global inventory lock. The result core is signed as `serverware.releaseCompletionResultSignature/v1` by the dedicated, globally separated `releaseCompletionResult` role. The caller independently pins that role's provider, key ID, SPKI digest, and final role-registry digest; the result's own fields and digest are not a trust anchor. Production custody requires an independently operated HSM/KMS or measured TEE and has not been exercised here. Final v1 is verified historical evidence, not an action capability; a stateful gate must recheck the live final head and atomically consume its redemption identity while performing the action. The launch schemas are [request v2](../schemas/launch-authorization-request.v2.schema.json), [authorization v2](../schemas/launch-authorization.v2.schema.json), and [bootstrap receipt v3](../schemas/bootstrap-receipt.v3.schema.json).

The current [launch manifest v3](../schemas/production-launch-manifest.v3.schema.json), generator, Make target, launcher, readiness verifier, and final verifier consume the authority, attempt-journal, witness, witness-store, global-role-registry, exact compact-v6-plus-LF, and full nested-v6 recomputation bindings. The previous public/final `public_verifier_bridge`, obsolete `final_completion`, live-result, final-identity, and missing-schema forms remain only as rejected compatibility cases. The current source remains unbuilt and unexecuted. Real independently administered TEE, KMS/HSM, witness, action-gate, production TLS, live-provider, and physical-YubiKey evidence remains absent.

### Response observation proof v1

`serverware.responseObservationProof/v1` is the external collector artifact for the all-method buffered observation contract. A client opts in with exactly one canonical, unpadded, 32-byte base64url `X-Serverware-Observation-Nonce`. The contract applies only after a CONNECT tunnel has been intercepted and its inner TLS session established. The complete request and emitted response must be buffered within the route limit and the global 16 MiB bound; it covers every HTTP method and body, including empty bodies, local policy or authorization rejection, upstream non-success, and response-validation blocking. An eligible flow permits zero or one upstream attempt and no retry. CONNECT establishment itself is outside the claim. Development `local-ephemeral` mode keeps a bounded in-memory reservation that binds both the request aggregate and the final statement digest; unlike custody mode, it is not restart-durable and is rejected for production completion.

The signed `serverware.responseObservationStatement/v1` contains commitments, counts, lifecycle states, release/runtime identity, and a nonce-contextual TLS exporter. It does not contain the raw target, query, headers, body, provider response, credential, or any credential-value digest. `credential.binding_digest`, when present, commits only to the non-secret credential reference and version. JIT, quota, credential, policy, and authorization fields are historical observations at the stated lifecycle points; they are not claims that those states remain current when a verifier later reads the artifact.

The wire response is HTTP/1.1 chunked, declares exactly `Trailer: X-Serverware-Observation-Proof-B64, X-Serverware-Observation-Proof-SHA256`, and sets `Connection: close`. After the final body chunk, the only valid terminal grammar is:

```text
0\r\n
X-Serverware-Observation-Proof-B64: <canonical-unpadded-base64url-runtime-proof>\r\n
X-Serverware-Observation-Proof-SHA256: sha256:<64-lowercase-hex>\r\n
\r\n
```

The digest covers the decoded compact canonical UTF-8 bytes of `serverware.responseObservationRuntimeProof/v1`. There are exactly two trailers, in that order, and no bytes follow the final CRLF. The gate fully buffers the emitted body and completes statement construction, signing, attestation, and policy-completion validation before publishing the response head or any body byte. It then holds one active-policy read lock across the complete bounded write of the response head, every body chunk, the terminal proof trailers, and flush; admission requires enough policy-trust freshness for that entire I/O window, and freshness is rechecked while writing. Policy replacement therefore cannot split a successful observation publication. The runtime proof remains proof-last on the wire because it appears only in the terminal trailers after the already committed body chunk. A terminal write failure can leave a generic client with a partial response and no valid proof; the strict collector must discard its private staging and must not finalize an external artifact.

The strict collector privately stages the response and accepts only normal chunked EOF with the exact terminal grammar. It validates the runtime and statement schemas, canonical statement digest, custody/server Ed25519 signature, nullable pre-dispatch or complete post-dispatch authorization evidence as applicable, fresh vendor quote and trusted-verifier statement, runtime/release/server/TLS bindings, aggregate commitments, and equality of its independently observed request and response commitments. The external `request` intentionally omits the fixed `body_observation: complete-buffered` field; its `aggregate_digest` is the statement request aggregate, recomputed with that fixed field restored. The external `response` is the collector-observed form of `emitted_response`. The collector capture preimage is the compact canonical object containing exactly `apiVersion`, `kind`, `captured_at_unix`, `request`, `response`, and `runtime_proof`. `collector.capture_digest` is SHA-256 of those UTF-8 bytes, and `collector.signature` is Ed25519 over the same bytes, following the existing collector convention. Only after all checks and normal EOF does it publish the proof artifact last through a no-replace destination; an existing output is never overwritten.

The response-path vocabulary is closed. `local-reject-no-upstream-attempt`, `dispatch-denied-no-upstream-attempt`, and `authorized-not-attempted` require `upstream_attempt: not-started` and a null observation. `upstream-attempt-outcome-unknown` means dispatch crossed the attempt boundary but no complete upstream outcome is known; it is not equivalent to no attempt. Complete released or blocked paths require complete headers and body commitments. `post-dispatch-local-failure` reports a local failure after dispatch and preserves the most precise attempt/observation state available. `unread` upstream bodies have null body fields; `incomplete` and `complete` bodies carry bounded digest and byte-count commitments.

Verification proves consistency among collector custody, the gate-authored observation, the signed authorization receipt when dispatch occurred, and the supplied vendor/runtime evidence. It does not prove provider truth, downstream application processing, receipt by a generic client, independent custody observation of upstream bytes or TLS, hardware TEE execution, or any nonce-free, malformed TLS, CONNECT-establishment, streaming, or Gmail-fanout flow. The observation authority is therefore fixed to `gate-authored`, `not-independently-observed`, and `not-claimed`.

Historical local status for that older snapshot: the gate, custody reservation/signing protocol, strict collector, development attestation fixture, closed Draft 2020-12 schema, release verifier, readiness runner, and Docker lifecycle were integrated. The Docker harness verified POST body commitment, local denial without upstream contact, response-reflection blocking, upstream non-success handling, body-limit retry, generic proof-last framing, attestation outage before response publication, and custody restart replay rejection. It also reopened, rehashed, and recounted the separately published body snapshot and refused aliases, hard links, symlinked parents, FIFOs, or replacement of an existing output.

Production completion accepts an independently selected `observation-v1` contract with the same independently pinned request, operation, nonce, TLS, trust, runtime, release, server, and authorization inputs as the other proof families. It independently matches the signed route to its credential requirement, JIT requirement, and exact shared-quota windows, rejecting credentialless or incomplete authorization evidence where that route requires atomic release authority. It preserves the statement's fixed `gate-authored`, `not-independently-observed`, and `not-claimed` authority limitations in the completion summary. It additionally requires an independently pinned single-link regular body-snapshot path and maximum no greater than 16 MiB; readiness and completion each reopen and verify the body against the collector and signed emitted-response commitments. Hardlinked artifacts and vendor quote bodies above the schema's 96 KiB decoded limit are rejected. This is implemented verifier behavior, not evidence that a real measured production custody runtime has emitted such a proof.

Three residual boundaries remain. An external mutating action can commit after dispatch but before proof delivery; Serverware cannot make that provider-side transaction atomic, so such routes need provider idempotency and explicit ambiguous-outcome handling. Credential acquisition or injection failures do not yet have a complete custody-signable pre-dispatch observation state. A lost atomic dispatch response is now labeled transition-unknown rather than denied, but observation v1 deliberately fails proof assembly because it cannot authenticate that disposition without signed authorization evidence. Real whole-codebase TEE execution, sealed monotonic rollback resistance or an independent witness, and target-deployment evidence have not been produced.

## Envoy Candidate Status

Envoy remains behind the Rust track until it proves all required production properties in `goal.md`: explicit HTTPS proxy CONNECT interception, dynamic attested leaf issuance, streaming request/response mutation, zero hot-path database/filesystem calls, and acceptable TEE TCB.

Current selection: continue with Rust as the production data-plane path. The Rust gate already has lower measured decision p99 than the mitmproxy end-to-end proxy path and keeps the policy/credential decision TCB small. Envoy should be revisited only with a runnable ext_authz/ext_proc plus explicit MITM proof harness, not as a generic forward-proxy configuration.
