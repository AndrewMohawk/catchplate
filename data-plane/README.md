# Data Plane Candidates

The production track is the Rust data plane. It owns policy evaluation, absolute-form forwarding, explicit CONNECT MITM, upstream TLS validation, scoped credential injection, response validation/projection, bounded credentialless and redacting stream modes, one-use shared JIT grants, and shared quotas. It is not an arbitrary streaming mutation proxy: each mutable format needs a dedicated bounded validator, credential-bearing opaque responses are forbidden, and credential-bearing mutating requests must be buffered and validated before release.

## Rust Decision Gate

Location: `data-plane/decision-gate-rs`.

The gate loads `/data/policy-bundle.json`, obtains the policy signing trust root from the control-plane attestation, verifies the quote and Ed25519 bundle, and checks a persistent policy high-water record before compiling principals and routes into memory. The same high-water check runs on hot reload, so stale signed sequences and rollback epochs are rejected across restarts while the last good snapshot remains active. Proxy forwarding and public attestation use port `9090`. Authenticated management calls use a separate `9091` listener that production does not publish. `SERVERWARE_POLICY_SIGNING_PUBLIC_KEY` remains only a test fallback; Docker uses the attested trust root.

The decision API covers:

- principal checks from source CIDR, trusted headers, and hashed `Proxy-Authorization` bearer tokens with token expiry and token-specific source CIDR binding;
- raw HTTP `CONNECT` preflight that denies missing principal identity, missing/bad/expired/wrong-source proxy tokens, unknown hosts, and unknown ports before leaf-certificate generation;
- explicit CONNECT TLS interception with cached dynamic leaf certificates signed by the verifier-installed data-plane CA handoff, including sequential keep-alive requests inside one intercepted tunnel;
- absolute-form HTTP proxy forwarding for policy-allowed `http://` and `https://` targets, with proxy-auth and Serverware-only identity headers stripped before upstream forwarding;
- upstream TLS validation through `SERVERWARE_UPSTREAM_CA_BUNDLE`;
- host, port, method, and path-template route matching;
- request-only adapter checks for `generic.rest`, `gmail.v1`, `x.v2`, and `npm.registry`, including bounded generic required request headers that are distinct from principal identity headers;
- shared route constraints for operation allow/deny lists, fixed-window credential quotas, query lookback windows, query numeric caps, JSON body rules, and JSON response date-window validation;
- authenticated shared quota consumption through `POST /api/data-plane/rate-limits/consume` when a `rateLimit` constraint uses `store: "shared"`, so daily or hourly credential budgets are atomic across Rust data-plane replicas;
- Gmail recent-query rewrite planning and unproven direct-message read denial;
- X read/write classification and credential app metadata binding;
- npm publish/dist-tag classification, required field extraction, and JIT-required decisions;
- canonical request and operation digests bound to policy hash, credential ref, and credential version;
- authenticated, non-authoritative local JIT grant cache through `POST /v1/grants` for dev fallback, addressed by principal, route, credential ref/version, policy hash, request digest, and operation digest;
- atomic one-use grant consumption through the shared control-plane grant endpoint before returning a credential injection plan when `SERVERWARE_CONTROL_PLANE_GRANT_CONSUME_URL` is configured;
- control-plane approval publish integration, with shared-consume digest parity tested against a real proxy-created npm approval;
- optional `SERVERWARE_EXPECTED_CONTROL_PLANE_QUOTE_KEY_ID` and `SERVERWARE_EXPECTED_POLICY_SIGNING_KEY_ID` startup pins so a replaced control-plane quote signer or policy signing key is rejected before any policy snapshot becomes active;
- signed policy hot reload from a background watcher, with no request-path filesystem calls and fail-closed last-good retention for invalid bundles;
- recipient-bound v2 leases for one exact principal/route/credential scope, with background renewal only for warm near-expiry scopes and synchronous fetch allowed on cold or expired misses;
- stale JIT grant invalidation when a fresh scoped lease rotates or removes the selected credential version;
- decision-time rejection for missing, deleted, or expired credential leases;
- caller-supplied `credentialVersions` ignored in favor of the authenticated lease cache;
- credential injection from recipient-bound leases during forwarding, while decision responses still carry injection plans by credential reference only;
- status-specific response contracts: `2xx` uses the success profile, `4xx`/`5xx` requires an explicit bounded error profile, redirects are blocked, and malformed or oversized bodies fail closed;
- structured response projection for Gmail, generic REST, X, and npm, including Gmail date proof and message-header filtering plus policy `allowedFields` redaction;
- policy-selected safe response headers limited to `Cache-Control`, `Content-Language`, `ETag`, `Last-Modified`, `Retry-After`, and `WWW-Authenticate`; state-bearing, redirect, hop-by-hop, encoding, and upstream framing headers are stripped;
- credential-bearing `response.mode: "any"`, non-redacting `response.mode: "stream"`, and credential-bearing mutating request streams rejected at policy admission;
- buffered response digest headers plus nonce-requested runtime proof headers; the external proof client emits `serverware.proxyResponseProof/v2`, binding request, operation, response bytes, policy, runtime, executable, release, instance, and TLS exporter;
- credentialless `request.bodyMode: "stream"` and `response.mode: "stream"` with backpressure, hashing, and size preflight;
- `request.bodyMode: "jsonlStream"` plus `response.mode: "jsonlStream"` for generic REST routes, redacting each JSON Lines record to configured `allowedFields`, enforcing `maxBodyBytes` and `maxLineBytes`, hashing raw and mutated bodies for audit, and covering both absolute-form and CONNECT MITM paths;
- `request.bodyMode: "jsonArrayStream"` plus `response.mode: "jsonArrayStream"` for top-level JSON arrays of objects, redacting each array item to configured `allowedFields`, enforcing `maxBodyBytes` and `maxItemBytes`, hashing raw and mutated bodies for audit, and covering both absolute-form and CONNECT MITM paths;
- `request.bodyMode: "jsonSseStream"` plus `response.mode: "jsonSseStream"` for `text/event-stream` JSON `data:` events, redacting each event payload to configured `allowedFields`, enforcing `maxBodyBytes`, `maxLineBytes`, and `maxEventBytes`, dropping arbitrary SSE metadata lines instead of forwarding possible secret-bearing fields, preserving only the `[DONE]` terminal marker, hashing raw and mutated bodies for audit, and covering both absolute-form and CONNECT MITM paths;
- `request.bodyMode: "jsonNestedStream"` plus `response.mode: "jsonNestedStream"` for arbitrary nested JSON documents, redacting objects and arrays to configured dotted `allowedFields`, skipping denied fields with serde's streaming deserializer instead of materializing them, enforcing `maxBodyBytes` and `maxNestedBytes`, hashing raw and mutated bodies for audit, and covering both absolute-form and CONNECT MITM paths;
- `request.bodyMode: "formUrlencodedStream"` plus `response.mode: "formUrlencodedStream"` for flat `application/x-www-form-urlencoded` bodies, redacting each key/value pair to configured `allowedFields`, enforcing `maxBodyBytes` and `maxPairBytes`, hashing raw and mutated bodies for audit, and covering both absolute-form and CONNECT MITM paths;
- `request.bodyMode: "csvStream"` plus `response.mode: "csvStream"` for CSV bodies with a header row, redacting each record by allowed header name, rejecting duplicate headers and records wider than the header, enforcing `maxBodyBytes` and `maxRecordBytes`, hashing raw and mutated bodies for audit, and covering both absolute-form and CONNECT MITM paths;
- bounded async emission for ordinary telemetry, plus synchronous durable control-plane acknowledgment of `data_plane.credential.release_started` before every credential-bearing upstream send; unavailable or rejected required audit returns local `503`, and JIT additionally requires its authoritative consume record;
- shared JIT grant consumption through `POST /api/data-plane/grants/consume`, so one-use grants are atomic across multiple Rust data-plane instances instead of process-local;
- verification of the control plane's attested Ed25519 response signature and every cleartext/decrypted recipient, nonce, policy, binary, issue-time, and expiry binding before a lease is accepted;
- a bounded, generation-scoped `Zeroizing` cache with monotonic version checks, final current/expiry validation before send, `0.25`-second Docker polling for warm-lease renewal, unexpired-only outage retention, and fail-closed behavior after expiry;
- lease metadata overrides caller-supplied credential metadata before adapter checks, and metadata-only credential updates advance `credential_version` so enforcement changes invalidate old grants and leases;
- fail-closed startup on unsigned, tampered, or wrong-key policy bundles;
- dev-mode `GET /attestation?nonce=...` with nonce binding, runtime manifest digest, running executable SHA-256 digest, active policy and high-water state, policy signing key ID, trust-root source, `serverware.sourceTree/v2` digest from release provenance, image signatures, scoped lease protocol, renewal bounds, and response-proof signing identity;
- CA private-key handoff only after the control plane's signed quote key-release gate authorizes `decision-gate-ca` for the release-pinned Rust binary digest;
- external-command TEE quote/KMS provider hooks plus an AWS Nitro-compatible control-plane provider that verifies CBOR/COSE_Sign1 documents, certificate chains, PCR allowlists, Nitro `user_data` claim binding, and a canonical KMS/HSM material-release command response before key handoff;
- explicit `hot_path.sqlite_calls = 0` and `hot_path.filesystem_calls = 0` in each decision response.

## Credential Lease Operation

Set `SERVERWARE_CONTROL_PLANE_CREDENTIAL_LEASE_URL` to `POST /api/data-plane/credential-leases` and provide the high-entropy `SERVERWARE_DATA_PLANE_AUDIT_TOKEN`. Each `serverware.credentialLeaseRequest/v2` names one principal, route, and credential and includes a fresh ephemeral X25519 key, one-use nonce, active policy hash, measured executable digest, and requested five-second TTL. The control plane verifies that exact assignment against the active signed policy and returns only that credential. Unknown fields, scope mismatches, nonce replay, wrong key IDs, stale policy, and wrong binary digest fail closed.

The response uses `serverware.credentialLeaseEnvelope/v2` and `X25519-HKDF-SHA256-AES-256-GCM`. AES-GCM AAD and the encrypted `serverware.credentialLeaseSet/v2` repeat the recipient key/nonce, policy, executable, principal, route, credential, issue-time, and expiry bindings. Rust first verifies the canonical HTTP response statement with the Ed25519 key obtained from attestation, then authenticates/decrypts, rejects unknown fields, and rechecks every binding. Cache commits are monotonic: lower credential versions and same-version secret or metadata changes are rejected, while a higher version atomically replaces only the same scoped lease.

Docker sets `SERVERWARE_CREDENTIAL_LEASE_POLL_SECONDS=0.25`. A bounded worker pool renews warm leases approaching expiry; the cache, work queue, and worker count are bounded and exposed in health/attestation state. Cold or expired misses may fetch synchronously, so lease acquisition is not fully off path. Failed renewal preserves a still-valid lease only until expiry, final forwarding rechecks that the selected lease is current and unexpired, and policy reload clears leases and grants.

Development Docker uses a software recipient and therefore does not protect process memory from host root. Production requires the recipient-attestation generator and control-plane verifier command pair; their v2 statements bind the recipient plus principal, route, and credential. This command contract is only an integration point. Real completion still requires NSM evidence binding the recipient key and scope to production PCRs, KMS `CiphertextForRecipient` delivered into the enclave, in-enclave unwrap/injection, and parent-host observation proving plaintext is not visible.

The active Python, Rust, and Docker paths do not use `/data/credential-generations.json` or plaintext `/data/credential-leases.json`; startup removes those legacy names and `.tmp` variants. Old snapshots and backups cannot be sanitized by startup cleanup, so rotate every credential that an older release published through those files.

Run it in Docker:

```bash
make bench-gate-rs
```

`make e2e` is the core Docker workflow and includes lease broker outage, expiry, and recovery. `make bench-gate-rs` is the broader Rust release-candidate matrix: forwarding and CONNECT, response profiles and stream validators, proxy response-proof capture, policy high-water/reload, shared JIT and quotas, audit, attestation, OAuth/control-plane checks, readiness fixtures, provenance, image signing, and the benchmark below.

This path avoids Docker Desktop host-port bridge jitter while retaining the deployed container network boundary. The evidence records distinct nonce-bound attestations before and after timing, plus the unchanged policy, immutable runtime-manifest, and executable digests. Mutable lease, cache, audit, and reload counters remain separate attestation status fields so ordinary traffic cannot change the measured runtime identity. Production release verification requires that executable digest to match both the key-release pin and the binary extracted from the shell-free production image.

Release provenance uses `serverware.sourceTree/v2`, whose digest commits to path, entry type, normalized executable mode, regular-file bytes, symlink targets, tracked deletions, every Git-tracked input, and relevant untracked source/build/config inputs. Build, provenance, image-signature, codebase-attestation, and release-verification paths must agree on that digest. This source binding identifies the authorized checkout; it is not evidence that the resulting Rust process executed inside a hardware enclave.

## Envoy Candidate Status

Envoy remains behind the Rust track until it proves all required production properties in `goal.md`: explicit HTTPS proxy CONNECT interception, dynamic attested leaf issuance, streaming request/response mutation, zero hot-path database/filesystem calls, and acceptable TEE TCB.

Current selection: continue with Rust as the production data-plane path. The Rust gate already has lower measured decision p99 than the mitmproxy end-to-end proxy path and keeps the policy/credential decision TCB small. Envoy should be revisited only with a runnable ext_authz/ext_proc plus explicit MITM proof harness, not as a generic forward-proxy configuration.

## Remaining Data-Plane Work

- Complete real recipient execution inside the production enclave: NSM evidence must bind the ephemeral recipient key to approved PCRs, KMS `CiphertextForRecipient` must reach that enclave, unwrap and credential injection must occur there, and parent-host observation must prove only ciphertext and digests are visible. The required production attestation command pair is integration wiring, not this proof.
- Preserve the release verifier's assurance ceiling: ordinary Docker, `/dev/nsm` access, quote-helper output, Nitro/KMS readiness, and fixture or self-reported evidence must remain `pre-enclave-readiness` with `hardware_proof:false`. Final v3 completion requires separately trusted fresh EIF/PCR, enclave CID/vsock, KMS Recipient key-custody, no-parent-key, release-binding, and current-host evidence. No current local artifact satisfies that final hardware contract.
- Extend `serverware.proxyResponseProof/v2` beyond `GET`/`HEAD` buffered CONNECT responses. Streaming responses currently expose bounded audit/digest evidence but no client-verifiable proof that binds the completed byte stream to the same TLS exporter and attested runtime.
- Extend beyond the current JSONL, top-level JSON-array, JSON SSE event-stream, arbitrary nested JSON, form-urlencoded, and CSV redaction set only when a specific API requires another bounded streaming validator such as multipart or XML.
- Point `SERVERWARE_COSIGN_BINARY` and the cosign key/keyless identity settings at production cosign/Sigstore backed by KMS/HSM or workload identity; Docker exercises the same fail-closed adapter contract with a local cosign-compatible fixture.
- Point `SERVERWARE_TRANSPARENCY_LOG_URL` or a log-specific `SERVERWARE_TRANSPARENCY_CHECKPOINT_COMMAND` at a public or managed production log for release channels; Docker exercises the same required-publish and signed-receipt contract with a managed-log fixture and an HTTP fixture.
- Build the production Rust data-plane candidate with `data-plane/decision-gate-rs/Dockerfile.production`, publish it by immutable digest, and run `scripts/verify_production_images_no_shell.py` through the readiness gate so the final image root filesystem contains no shell binary.
- Generate agent enrollment packets with `scripts/generate_agent_enrollment.py`, apply their deny-by-default egress policy, and set `SERVERWARE_AGENT_EGRESS_*` readiness variables so agents cannot bypass the Serverware proxy.
- Run `make verify-apparmor-runtime` on a Linux Docker host with AppArmor enabled; Docker Desktop runs `make verify-apparmor-contract` to prove the checked-in profile and Compose override cover every service.
- Run `make verify-production-readiness` in the production release environment with a real Nitro NSM attestation helper, production KMS/HSM unwrap command, production cosign identity, production transparency log URL, and Linux AppArmor enabled; Docker now verifies those command schemas and fail-closed checks with local fixtures. Treat a pass as release readiness, not final enclave proof, until the independent hardware-assurance inputs above also verify.
