# Fresh consume: private prepare and export

`control_plane_oidc_session_activation_completion_recovery_consume_planning`
connects acknowledged activation completion to private consume planning on the
actual fresh `_ConsumeAttempt`. It neither creates nor relaxes
`_ActivationPermission`. The actor has the distinct `consume` purpose and
`activation` profile; a closed activation or recovery permission cannot be reused.

## One actual owner and existing consume slot

`_prepare_on_active(active)` accepts no permission, successful result, replacement
request, key or allowance. The exact source owner and its one-use
`_require_planning_call` hook must establish the successful existing consume-slot
claim, retained raw2 input originals and genuine same-call `_InputMaterial`.
The root claim precedes input issuer contact. A stored or recovered claim cannot
resume acquisition or planning, and an absent record is not proof of SQL
non-execution.

The immutable raw16 remains the actual activation raw13, canonical expectations,
activation before-vector and old64 possession. Its fields must be the original
objects selected from the genuine activation controls, original or separately
reconciled acknowledged raw4, root enrollments and fresh actor. The module opens
no new work ledger or processing window.

## Independent original admission

The returned planner/history bytes are freshly admitted by the existing root
verifier against actual parent configuration, generation, runtime identities,
planner keys, measurements, endpoint and state enrollment. The incoming
`_InputMaterial` is retained as a source association, never passed as an authority
argument to that verifier. Its already-held request length is used only for
preallocation and then byte-joined to the freshly admitted request.

The helper independently joins the original activation expectations, caller
digest, reservation ACK and pending scope. The consume before-vector must equal
both the root planner's complete vector and the genuinely acknowledged
activation after-vector. The typed request must preserve the original eight
activation arguments, exact current target, deterministic delivery ID and
old-token commitment. Original planner/history launch restrictions remain live
and only narrow the same window.

## Prepare, retain, admit; then export, retain, compare

One bounded prepare call sends the existing private raw16 transport form:
purpose, old64, activation raw13 and original deadline. Its opaque raw6 response
is durably retained through the guarded same-work custody method **before** any
status or signature admission. Uncertainty is terminal and does not authorize
an export or retry.

For a prepared response, the request must byte-match the independently admitted
typed request. Returned scope must equal the independently derived subject and
policy scope, with a deadline no later than the original allowance. The actual
planner signature, plan identity, age and expiry are authenticated. The private
planner bounds that signed expiry by its actual write/delivery expiry; the
public continuation adopts that restriction and never creates or renews dates.
The returned journal digest is an exact locator, not a signature or replay proof.

One bounded export call then uses that signed original, deadline and locator.
Its opaque raw7 is retained before status or correspondence checks. All five
non-ciphertext fields must equal the prepared originals. The transport bounds
the distinct ciphertext frame; this public module cannot open it or claim
private replay, SQL execution or token release.

## Private continuation and cleanup

The private sealed `_ConsumePlan` retains `before`, `prepared`, `exported`,
`material`, `signed`, `scope` and `original_reservation_bytes`. Its dynamic
`window`/`deadline_ns`, `current`, `narrow` and `continuity` remain bound to the
same exact active owner. Canonical public graph pins and original references
detect replacement; clocks and allowances cannot widen.

The owner retains the full plan guard separately through normal actor cleanup.
The plan's ancestor calls only the owner's original guards, never itself.
After owner cleanup this continuation is unusable. It is not a public success or
an authorization carrier for a later request; subsequent consume authorization,
SQL and completion require the same properly scoped continuation to be wired.

## Combined capacity, not a renewed allowance

The root reserves the shared 32 MiB acquisition/planning lane exactly once
before the first historical target body, within the original 64 MiB aggregate.
Input raw2 is capped at 256 KiB. Its genuine acquisition captures remain held
while new planner/history admission and preparation/export run. Temporary
journal I/O has a separate 2 MiB slice inside the same lane.

Before fresh root decoding, actual original lengths and measured fixed public
configuration graphs reserve new admission/canonical/vector representations.
The typed-request reserve uses its actual already-held length, not a second
unused 2 MiB maximum. The independent scope is a fixed root-payload projection
with bounded field-name/deadline overhead. Prepare/export caps retain multiple
response footprints and leave later-export headroom; they also tighten to the
publication slice after conservative selected-history/header accounting. The
guarded journal independently preflights actual selected encoded sizes before
reading or writing. No caller double-charges its I/O or wraps it in an opaque
callback.

Larger valid histories may fail closed. These are conservative representation
reservations, not Python heap/RSS guarantees. This source slice is private only:
no public action, authorization grant, SQL dispatch, token or session cookie is
enabled. It is unbuilt, unexecuted and unprovisioned; no runtime success is claimed.
