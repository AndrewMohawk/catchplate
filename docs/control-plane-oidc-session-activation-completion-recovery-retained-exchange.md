# Reconciled completion: protected RECOVERY exchange

`serverware/control_plane_oidc_session_activation_completion_recovery_retained_exchange.py`
connects one fresh `retained-release` actor to the independently authorized
RECOVERY/checkpoint-one worker. It accepts only the actual source-owned
`completion_recovery_delivery._DeliveryAttempt`, not a posted subject, request,
permission or successful-result carrier. Preparation and LIVE delivery retain
their separate purposes and entrypoints.

## Original association and fresh authority

The owner must have finished genuine raw3 grant admission and one worker staging
exchange before selecting the terminal or invoking this helper. Its stage flags
are true, its protected-exchange latch is already spent and in progress, and its
actor, controls, genuinely verified raw6 completion, sealed input/intent/proof
continuations, root, independent recovery configuration and originals remain the
same actual objects. The old cookie supplies only signed old-token possession.

The input helper's `_admit_for_retained_release_on_controls` selects the existing
delivery owner's private provenance handshake under the distinct literal
`retained-release`. Intent/proof readmission requires existing originals and
uses historical verification. It cannot sign, contact setup/proof services,
publish missing preparation records or borrow a closed preparation permission.

The optional public terminal is the exact existing `_StagedRecoveryResponse`
from `completion_recovery_delivery_response`. It selects the original ancestor
**before** new recovery derivation and admission. The prior acquisition result
is retained as an original association, but its `live` guard is never attached
to the new verifier ancestry: that ordinary actor path must remain closed after
normal cleanup. Without a terminal, the helper remains live-context-only.

## Genuine re-derivation, not private-store inference

The request prefix is raw7 `(RECOVERY purpose, proof, proof enrollment, intent,
intent enrollment, old64, encrypted envelope)`. Its envelope comes from the
actual verified raw6 completion hints, not a different history record. Hint
packet, effects, envelope commitment and original dates must match the sealed
release expectations. The proof custody and both enrollments byte-match the
independent recovery configuration and original actor pins.

The existing original-only recovery derivation genuinely authenticates the
independent root policy, historical intent/proof/custody and old-token
possession. It reconstructs the canonical outcome, compares its independently
pinned digest, and creates the real raw8 request and request identity. The
canonical outcome must byte-equal the retained raw3 outcome; the policy identity
must equal the genuinely acquired policy. Complete release expectations, proof
scope, caller, custody/intent identities and actual signed state receipt also
join the sealed input and proof originals. The original activation planner is
checked as an exact original.

A fresh client/server admission uses the independently derived scope, not an
incoming signed scope copied as its own expectation. It requires RECOVERY,
checkpoint `{recordCount: 1, outcomeDigest: <independent pinned digest>}`, the
matching recovery scope, exact custody, independent launch and release binding.
Client/server intervals remain contained in the fresh policy interval. The
original delivery expiry is not renewed. The protected endpoint comes from that
policy, never from a LIVE handoff or the issuer-acquisition socket.

Neither reconstructed outcome bytes, retained grants nor staging ACK prove
that a private outcome exists. Actual checkpoint-one worker/store admission is
still required. Missing local records cannot select a checkpoint, authorize a
fallback or prove non-execution. No outcome is appended and no SQL is retried.

## One claim, socket and genuine receiver

The guarded custody method
`claim_oidc_session_activation_completion_recovery_retained_release_attempt`
directly charges the original work and irreversibly claims the existing global
client-authorization slot before the sole protected socket. It records only
authorization, request, RECOVERY profile, server and expected-outcome scalar
bindings. A duplicate or recovered claim refuses; there is no automatic retry.

After normal socket close, the actual response verifier independently admits
the original request/grants and exact token commitment. Its full current guard
is retained separately by the owner and, when selected, the terminal; no child
is fed into its own ancestor. Only that genuine verifier returns token64 to the
actual owner. This module does not log or persist tokens/requests, open AES,
perform current-auth or set cookies. Current-auth, normal cleanup and signed
cookie sending belong to the separate exact terminal boundary.

## One original capacity reservation

The owner reserves 16 MiB exactly once before its first historical target body.
Grant acquisition has a temporary 2 MiB journal I/O slice and a 128 KiB total
raw3 ceiling inside that lane. Temporary I/O may be reclaimed; genuinely held
policy/grant/server representations remain reserved through the exchange.

Before decoding hints or new authority, actual lengths compose the shared
acquisition-capture reservation, read-only derivation/outcome capacity, two
genuine receiver reservations, raw3/framing/hint copies, a fixed claim allowance
and 256 KiB terminal/current-auth headroom. Their sum must fit the same 16 MiB;
already-held parent/history representations plus that sum must fit the original
64 MiB aggregate. The final receiver receives the additive held reservation.
No new work ledger, window or transport allowance is opened.

Larger otherwise valid originals may fail closed. These are conservative byte
representation bounds, not Python heap/RSS guarantees. This is source-only,
unbuilt, unexecuted and unprovisioned; no runtime delivery is claimed.
