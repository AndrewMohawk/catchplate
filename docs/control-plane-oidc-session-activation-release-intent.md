# Same-context release-intent production

`control_plane_oidc_session_activation_release_intent.py` connects the actual
live permission context's acknowledged consume completion to one dedicated
release-intent signature and exact token-free retention. It returns signed
original bytes only. This source has not been built, executed or provisioned;
intent is not committed-release proof, token opening or a public handoff.

## Actual owner, key and inputs

`permission.authorize_release_intent()` takes no arguments. The cold owner's
matching private facade enters only its existing active permission slot. There
is no accepted target graph, successful result object, recovered context,
caller-selected work/window, signing key or posted token.

Explicit cold [intent configuration](control-plane-oidc-session-activation-release-intent-bootstrap.md)
holds the original root enrollment, independent six-field scope and actual
forbidden-key tuple. The root owner retains the distinct FD207 private key and
its original identity. The coordinator genuinely re-admits that enrollment,
checks its original digest/public-key binding and pair, and preserves key/FD,
HTTP-purpose, parent custody, same-PID/thread and original permission continuity.
Activation and consume execution keys are not relabeled as intent keys.

Only acknowledged [same-context consume completion](control-plane-oidc-session-activation-consume-completion.md)
with explicit consume configuration v4 can enter. Existing v3 remains the
raw4 completion profile and cannot produce intent through this path. The v4
exchange receives raw6 internally but `complete_consume()` still returns only
the existing raw4 completion response. The two extra hint frames are retained
privately, not appended to that return.

## Known bindings versus hints

The original activation/consume request expectations provide exact user,
session, credential, binding challenge, token commitments and assertion
identity. The retained permission binding supplies the actual user/session/
credential identity; the original credential tuple supplies its record ID.
No nonexistent credential-record field is inferred from the HTTP binding.
Original reserve and complete/state ACK signatures bind pending ancestry,
completion-request identity and the full after-vector. These original controls
are genuinely checked again on the same work; their prior successful carrier
is not submitted as new authority.

The two [hint originals](oidc-session-activation-release-hints.md) contain a
packet digest and a closed descriptor with an effects digest, encrypted
100-byte delivery envelope and original creation/expiry timestamps. These
remain **untrusted expectations**. The caller cannot derive the private
selected rows/mutations/result/work-unit graph from public control digests.
It does not turn the hint data into authenticated packet, effect or delivery
state. The actual old cookie must remain unchanged and its 64-byte original
must match the expected old-token commitment; no posted digest substitutes for
possession.

The coordinator constructs exact release6 and consume-binding5 from this split:
known subject/request/completion/vector identities, plus the bounded hint data.
It hashes the encrypted envelope, uses the original delivery-scope grammar and
passes those exact expectations to the existing genuine
[intent producer and verifier](oidc-session-activation-release-intent-admission.md).
Their deterministic activation/delivery joins, enrollment, nonce generation,
possession and signatures remain mandatory. Later private committed-release
proof must independently replay and match every hinted binding. A wrong hint
can make that proof fail, never authorize opening.

## One-use publication and lifetime

The context spends its intent latch before callbacks. After bounded original
and target admission, it durably publishes `release-intent-claimed` under the
same live consume/activation claim before the actual producer or nonce/signing
operation. The producer's signed bytes undergo genuine original signature
readback and lifetime narrowing, then exact `release-intent` raw1 publication
before return. Raw4 completion and raw2 hints were already retained, in that
order, before status or signature interpretation. No old/new token, cookie or
assertion enters these journal records.

All work, original epoch/monotonic brackets, root lifetimes and current guards
are inherited. A private restrictive continuity hook passes only increasing
clock floors both ways between the actual owner and intent implementation.
It cannot replace work limits, lower metrics, renew a window or bypass original
admission. Returned floors are checked against the currently narrowed epoch
expiry and monotonic deadline before return. Delivery expiry, enrolled age/skew
and signed intent expiry can only shorten the live context, including its exit.

Any failure revokes the context. The durable attempt remains terminal even if
signing or publication was uncertain; recovered records cannot authorize a new
nonce, replacement intent, retry or resumed context. No grant/proof/client
exchange occurs here. Post-intent root custody, private proof production and
configured protected token handoff remain later connections, with independent
per-request issuance/provisioning still required. Public routing/cookie release,
separately authorized recovery and production acceptance remain open.
