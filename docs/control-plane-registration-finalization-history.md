# Historical finalization subject resolution

The actual finalization completion-subject path uses
`control_plane_registration_finalization_history.py` and returns a private
same-call material to the completion/recovery caller. The legacy tuple projection
remains for compatibility; it is not a successful-verification input API.
This is source-only integration, not a build, runtime or production acceptance.

## Two independently selected historical scopes

The optional parent `finalization_history` is cold-admitted with the exact
existing `registration_history` archive. It adds genuine historical finalization
enrollments/root, pending predecessor, authorization and completion packet pins;
retained records cannot appoint that archive or add a key.

An original finalization intent first locates an already admitted static verifier
key. Its actual signature, configuration/generation/operation and all detached
body commitments are checked before its historical context is decoded. The
authenticated planner receipt and original evaluation time then select the
archive snapshot and independently configured finalization scope. Full original
caller, intent/relay, proof, typed request and vector/grant replay still follows.

The associated registration evidence takes a separate path: its genuine original
request/response controls authenticate its context before selecting its own
registration snapshot. That scope supplies the old root, enrollment originals
and pending pins for actual acknowledged evidence-completion verification.
The genuine signer replay uses this independently selected registration scope,
not finalization's configuration. Signer configuration, generation, keys,
identities and original control intervals must agree; differing signer/evidence
cohorts refuse rather than silently sharing current pins.

The complete finalization request is regenerated from that signer, then its
request/operation IDs, exact inputs and user/session/challenge/mode are joined to
the actual finalization. Old finalization and registration scopes may differ;
neither may be inferred from unsigned SQL data or a stored status marker.
The current owner still supplies the endpoint and fresh public permission.

## Inventory, lifetime and continuation

One existing bounded combined read holds finalization preparation/reservation/
outcomes and the associated registration/signer/outcomes. Before its first body,
the original 64 MiB accounting ceiling reserves measured sealed-parent copies,
both historical original/capture inventories, six cold enrollment originals,
two regenerated request buffers, metadata, and eight maximum-sized future
completion-response representations plus 64 KiB framing headroom. Caller-supplied
additional bytes only subtract from this allowance. The reader gets three eighths
of the remainder; its own `3 * selected encoded bytes + 16 KiB` preflight leaves
eight selected-original representations for genuine replay. Returned concrete
sizes and the final reservation are checked again before admission.

These conservative byte-representation reservations are not a Python heap/RSS
guarantee. Large valid histories may be refused. All reads, signature checks and
graph guards consume the same work; no callback wrapper resets a metered reader.

The original processing window is only narrowed to the present archive lifetime.
Full `current()` retains and seals both selected configuration graphs and the
entire loaded replay inventory. It remains mandatory through genuine finalization
acknowledgment admission. A separate `continuity` function captures only actual
cold owner/archive references and clock floors, not records, subject or selected
graphs. A downstream prerequisite consumer may keep that narrow guard and its
own pinned scalar projection only after it has genuinely admitted the exact
acknowledgment and discarded the complete replay material. Deleting tuple aliases
while retaining full `current()` does not release its inventory.

The public inspection facade checks the full guard after normal owner-lock exit.
Historical signed expiry never becomes current authority or renewed SQL
permission. Missing records and original uncertainty do not authorize retry.
Unknown source revisions remain unsupported; no signed source field or global
revision is rewritten. Full activation historical authority and explicit older-
source adapters remain separate H05 work.
