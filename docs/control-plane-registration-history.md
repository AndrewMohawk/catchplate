# Historical registration subject resolution

`control_plane_registration_history.py` is the original-only resolver used by
the actual registration recovery-subject facade. The completion recovery caller
retains its selected scope through pending, grant and completion admission; see
[historical completion recovery](control-plane-registration-historical-recovery.md).
This is source-connected functionality, not an executed or production-accepted
recovery demonstration.

## Independent authority and original replay

The optional parent `registration_history` material contains the genuinely
root-admitted archive and separately configured historical registration
enrollments, pending predecessor and completion packet. A retained local digest
is only a locator. An original planning control's configuration, generation and
issue-time fields first locate an already admitted static verification key.
Genuine request and response signature checks authenticate the exact original
body commitments before the evaluation context is decoded for final selection.
Its planner receipt and historical evaluation time select only an existing
archive snapshot, never a new trust root or posted key.

The selected independently admitted configuration, root and original caller,
grant and state enrollments feed genuine historical signer and full execution
exchange replay. Request digest and operation ID must join the same seven-field
subject projection. Authenticated request/response, caller/grant and signer
source/enrollment/evidence intervals must fit the selected historical snapshot.
Those old intervals never become the present clock or renewed permission.

When history is disabled, genuine same-current-configuration replay remains.
When enabled, an unknown or ambiguous archive/scope fails closed: there is no
fallback to current pins. Original source labels and signatures remain intact;
only the source revision supported by the actual verifiers is admitted. There
is no global revision mutation or older-source compatibility adapter. H05 also
still needs the other historical consumers and explicit source-version support.

## One bounded owner and inventory

`_replay_material_on_owner(..., _include_outcomes=True)` directly invokes the
combined journal read on the original work and guard. It holds the exact
execution/signer pair plus all present registration outcomes in one preflight;
inspection uses the corresponding metered preparation-only read. Neither call
wraps the charging reader in a separate work callback or scans unrelated data.

Before the first retained body, the resolver subtracts measured sealed-parent
representations, archive captures, known enrollment copies, two regenerated
request buffers and a conservative future completion-response/framing reserve
from the existing 64 MiB ceiling. It passes three eighths of the remaining
capacity to the reader, whose own `3 * encoded inventory + 16 KiB` check leaves
eight selected-original representations for replay. The concrete returned
inventory and final reservation are checked again before cryptographic replay.
The optional additional byte count can only tighten that same allowance.
These are conservative source-known byte-representation reservations, not a
Python heap/RSS guarantee; large otherwise-valid inventories may be refused.

The original processing window is only narrowed to the current archive's
valid-until time. Actual owner identity, archive lifetime, both clock floors,
selected configuration graphs and immutable output associations remain guarded
on the same work. Pure bounded historical verifiers are bracketed by that guard.
The private result is not an incoming successful-verification carrier.

Current actor permission and transport endpoint still belong to the current
owner. Historical scope grants no new SQL execution, retry, finalization or
token delivery. Missing outcomes prove neither nonexecution nor rollback;
original uncertainty and existing irreversible claims are preserved.
