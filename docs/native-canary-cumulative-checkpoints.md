# Native cumulative checkpoints

This source slice connects the real accounting ledger to the existing durable canary sender. It has not been built or run. It requires the paired native heartbeat/delivery-v2 source and its explicit cold selection; old delivery-v1 and legacy Fleet formats remain unchanged.

## Actual producer and consumer

Successful `record_admission` and `record_with_original` retain the exact returned, verified signed spill receipts before advancing the local contiguous head. The history starts at the actual installed load's authoritative ordinal/head, not an assumed zero. Compaction cannot discard these originals. A sealed `NativeAccountingSnapshot` is created only while holding the actual current-generation and accounting-ledger guards; the retained trusted clock is sampled under that ledger lock. It is a complete prefix through the retained contiguous head, not proof that all concurrent work has drained.

The existing compaction worker fixes one processing deadline before its actual custody call. After its interval has been definitely consumed, it calls `native_canary_heartbeat::checkpoint` under that same original deadline. The returned object owns the exact snapshot and full heartbeat original whose independent native purpose was accepted through durable prepare/read/claim/intake. There is no second periodic heartbeat producer or reconstructed successful-heartbeat DTO.

The cumulative producer rechecks actual retained assignment, load/runtime/publication, current key trust and every original role signature. It derives the twelve event counters and both ordered Merkle roots from all original receipt bytes, including genuine exclusion/failure labels. The raw opening receipt remains distinct from a legacy Fleet ingress envelope. Present public keys come from their exact independent custody assignments; no generic signer or new key alias is introduced.

One irreversible attempt reserves the generation's next cumulative sequence and previous full-record digest. The closed `serverware.nativeCumulativeCheckpoint/v1` record carries the full heartbeat, the exact completed compaction receipt identity, accounting originals and keys. It goes through the same retained sender's protected prepare/read/claim/one-contact protocol. Only an authenticated consumed completion containing that exact original advances the local sequence. Unknown, expired, capacity, changed-owner or serialization outcomes permanently fence observation; there is no fresh request ID, deadline reset, replay or reboot reconstruction of contact permission.

The controlled intake independently re-admits the nested heartbeat purpose at verifier and planner. In the transaction it requires its exact previously committed heartbeat original/result, current protected assignment/load/publication and unrevoked role keys. It recomputes every signature, original record/head digest, contiguous ordinal, opening association, counter and Merkle root. The complete protected batch inventory supplies the prior cumulative head and compaction original. A successor must strictly extend the exact old signed prefix; neither another native boot nor a new request ID resets it. The existing transaction retains the full new original/result, audit and delivery consume atomically. No legacy checkpoint or readiness row is synthesized.

## Bounds and remaining conditions

Retention is capped at 64 originals, 64 KiB each and 512 KiB total per generation. Its conservative serialization charge debits the existing 128 MiB queue pool, including snapshots that outlive the generation. No global transport, proof, table or work ceiling is increased. The record limit is 768 KiB inside the existing 1 MiB batch; the whole retained snapshot/argument/proof/result limits may refuse earlier. Every inner inventory/signature is charged against the existing 8192-unit transaction limit. Large assigned-key inventories or the existing 32-row journal cap therefore reduce usable capacity. There is no eviction or silent restart to recover capacity; production-scale authenticated retention/retirement remains required.

This is cumulative **prefix evidence**, not full readiness. It does not certify a sealed observation interval, drained outstanding requests, client receipt, complete fleet membership, complete required-route/response-obligation coverage, allowed expansion matrix, acceptable latency/error thresholds, or a closed heartbeat window. The current trigger is the real compaction cadence (prefix 8, trigger 16), not an idle/final sealing scheduler. Genuine sealing/drain and a full native readiness consumer with those conditions remain required, along with independently authorized restart/generation succession and scale capacity. The chosen end state is an explicit native profile with equivalent full guarantees, not fabricated Fleet signatures or interval-only readiness.
