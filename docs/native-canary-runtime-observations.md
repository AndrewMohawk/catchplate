# Native terminal and candidate request observations

Source slice only; no build, provider contact, runtime acceptance, or readiness
claim. This extends the genuine opening exporter and the retained v19 durable
delivery owner. It introduces no new cold profile or signing permission.

## Connected producer and receiver

The actual serving `Arc<GateState>` installs one weak observation-owner binding
before serving. Successful selected capture retains that binding and the exact
definitely consumed opening's generation, ingress sequence, request binding,
request commitment, and signed opening receipt hash. No independent GateState,
signer, TLS transport, or native owner is reconstructed for the worker.

`ShadowRequestHandle::finalize_terminal` already derives the final active outcome
from the real local-response/deny or post-dispatch completion path. Its existing
prepared record checks the active plan, actual effect commitments, returned
status and response commitment before append; the matched record binds the
genuine successful terminal receipt. The accounting owner now returns that
original alongside its existing fixed-size durable reference. Only after the
successful lifecycle state update is this exact original exported. Candidate
work is enqueued afterward, so it cannot export ahead of its terminal.

The actual `shadow_worker` evaluates the candidate request plan against retained
request facts and the active decision-time/credential bindings. Only a validated
candidate plan and successful `CandidateEvaluated` ledger append reach the new
exporter. The exporter carries that existing signed receipt unchanged. It does
not rerun a decision, invent a success DTO, ask for a new signature, or export
request bodies or injected credentials.

`catchplate.nativeCustodyRuntimeObservation/v1` is a closed 12-field carrier of
the original 21-field receipt. Terminal uses the independently assigned
`CustodyTerminalAppend` key/domain; candidate uses `CustodyLedgerAppend`. Both
retain the assignment-bound production custody proof scope and full raw signed
event bytes. These are not legacy `FleetIngress`, `FleetActiveDecision`, or
`FleetShadow` signed envelopes. Older paths remain unchanged.

The controlled receiver rechecks actual protected assignment/load/publication,
current role revocation and complete key independence, then verifies the exact
original dedicated signature. Complete authenticated batch populations must
contain exactly one matching opening, and exactly one prior consumed terminal
for a candidate. Another UUID cannot replay or replace either observation.
Generation, request commitments, ingress sequence, ordered receipt time/ordinal,
and the active plan/final-decision/effect commitments must match. Intervening
spool ordinals may belong to concurrent ingress: this is not complete-range
proof. Batch original, result, audit and exact delivery-slot consumption commit
atomically through the existing writer.

## Lifetime, uncertainty and capacity

Each genuinely new observation receives one fixed delivery-processing deadline
when appended, clipped by the original retained native lifetime and unchanged
assignment/generation validity. A long request does not reuse the already
consumed opening's 30-second HTTP transaction window. Signed receipt timestamps
are never refreshed. Local phase is irreversibly consumed before preparation;
the existing unresolved protected sender head blocks replacement or retry.
Unknown/failure hard-fences the runtime and future openings. A failed export
does not erase an already dispatched effect or prove a response reached a
client. Restart recovery remains authenticated observation only.

The queue conservatively charges an additional 2 KiB per job for fixed lifecycle
references. The complete record is capped at 64 KiB, raw event at 16 KiB, and
the assigned inventory at 256 keys. Existing whole-response, batch, table,
query and work limits are unchanged. Increasing production-scale retention
requires its own bounded capacity work; no automatic eviction is introduced.

## Remaining required producers and consumers

This connects real terminal active commitments and candidate **request**
observations, including local deny and completed-response paths. It does not
claim actual client receipt, candidate response-validation coverage, complete
terminal ingress ranges, physical storage, checkpoint or readiness acceptance.
The existing response-comparison worker is connected separately by the additive
[response observation profile](native-canary-response-observations.md); it is
not relabelled as covered by this 12-field profile.
Initial complete fleet/role inventory, remaining twelve-kind native producers,
range/checkpoint assembly, readiness and final protected Setup handoff remain
required follow-on implementation, not user-upload or provisioning substitutes.
