# Native terminal and definite reservation refusal

This is a separately selected successor to [native Ledger storage](native-ledger-spool.md), not an expansion of old grants. It supplies the actual `AppendTerminal` caller and a definite `ReserveSpoolAppend` unavailable outcome. The prior no-generation `UnavailableIngress` authority, active-effect barriers, active-effect commit/reconciliation and compaction remain separate producers. No timeout, storage error, absent response or uncertain transition becomes an unavailable receipt.

## Selection and independent authority

The paired shape is [native-ledger-completion.v1.schema.json](../schemas/native-ledger-completion.v1.schema.json). The fixed eight-child cohort admits Retrieval, Persistence, TrustedTime, GenerationInstall, LedgerAppend, IngressAdmission, TerminalAppend and Bridge under eight distinct actual identities. The retained parent release, inspection and cleanup owner must select its explicit eight-child successor; seven-child cleanup cannot account for it.

| Owner | Explicit selected successor | Signed grant |
| --- | --- | --- |
| TerminalAppend | `nativeShadowTerminalSpoolGuestLaunch/v1`, `terminalSpool` pin | `nativeShadowTerminalSpoolServiceAssignment/v1`, purpose `native-terminal-slot-append` |
| LedgerAppend | `nativeShadowCommitRequestGuestLaunch/v3` | `nativeShadowLedgerSpoolServiceAssignment/v2`, purpose `native-ledger-spool-and-sampling-with-unavailability` |
| Retrieval | `nativeShadowRetrievalGuestLaunch/v3` | `nativeLedgerSpoolRetrievalGrant/v2`, required exact TerminalAppend role key |
| Bridge | `nativeProofBridgeLaunch/v4`, runtime `policyCustodyProductionRpcRuntime/v8` | `nativeSpoolServices/v2` retaining both full service-grant originals |
| DurableRecoveryStore | Existing ordinary runtime/v7 and actual private spool journal | `nativeSpoolHeadGrant/v2`, required `completion:{terminal,regularAppendCapacity}` |
| CurrentSignatureAuthority | Existing ordinary runtime/v7 and actual private current journal | `nativeSpoolCurrentGrant/v2`, exact full HeadGrant/v2 original |

Every API above has its `serverware.` prefix. Native grant signatures select the exact matching `serverware.<grantName>.signature/vN` domain; service-root grant signatures use the existing service protocol framing with the explicit v2 domain. These retain the existing independent supervisor/service roots, full assignment/key-authorization originals, current revocation checkpoint, whole trusted-time interval and original boot/lifetime scope. TerminalAppend receives only its independently assigned TerminalAppend key, never LedgerAppend's key or HMAC. IngressAdmission remains independently keyed and has no HMAC. The real Ledger owner keeps only the source-fixed sampling and protected-request commitment operations already authorized by its own assignment.

Terminal's fixed listener is `/run/serverware-shadow-terminal-append/listener.sock`, activation `terminal-append-listener`, with separately retained parent inspection. The bridge uses `terminal-append-peer-directory`. It is not a new generic signer endpoint. `Configuration::completion_selected()` is true only for the Terminal/v1 or Ledger/v2 grant, and retrieval's getter only for RetrievalGrant/v2. Both are admission selectors, not readiness verdicts. The actual `mod.rs` preparation joins are `open_completion`; the bridge calls `proof_client::Prepared::open_terminal`. No new `AdmittedGuest` field is needed.

## Actual effects and consumers

1. The existing lifecycle constructs `TerminalSlotAppendRequest` from its actual pre-dispatch or post-dispatch event and calls custody `append_terminal`. Its request identity retains the genuine early sampling original from the admitted opening. That digest is not relabeled as the later ProtectedRequestFacts commitment.
2. The real DRS admits the exact request under the installed generation owner, verifies the retained opening, takes the next shared event ordinal/head and durably records an allocation. A terminal can be allocated only once for that ingress, with no pending reservation. Later legitimate candidate/response ledger records are not confused with a second terminal.
3. The separately admitted Terminal owner verifies that allocation and its complete scope/currentness, retains one preparation and signs the typed core. The actual Retrieval owner stores the core with its existing fs-verity, bounded journal, fsync/readback and signed storage original.
4. The Terminal owner checks that full storage original before signing the complete final terminal receipt. DRS verifies it and durably advances the shared head; Current verifies the real DRS transition and durably records its independent transition. The native owner completes only against those exact originals. The bridge then retains the final dispatch original through actual Persistence before clearing its in-flight state.
5. The receiving custody process independently verifies the terminal signature, current assigned purpose, exact event and retrieval/persistence proof before returning `TerminalAppended` to the real lifecycle caller. This native producer emits only `Committed`; it does not manufacture `Existing` or `Fork` receipts to repair a lost response.

For regular reservations, HeadGrant/v2 admits `regularAppendCapacity` in **1..32**. DRS derives `committedRegularAppends` exclusively from successful retained regular `Append` completions in its complete journal. When the committed count equals the signed capacity, the original Reserve call receives a real DRS-signed `ReservationUnavailable` allocation decision. Ledger produces a stored, signed spill with disposition `unavailable`, and DRS/Current/Persistence complete the same actual durable sequence. The same reservation result kind contains the closed wrapper `nativeSpoolReservationOutcome/v1` with `result:{outcome:"reserved"|"unavailable",receipt:...}`. Its outer service result remains a genuinely sealed DRS artifact.

The receiving native custody branch verifies the actual spill and its proof before constructing the existing typed `SpoolAppendReservationOutcome::Unavailable`. It never retains that result as an append capability. This refusal is a reached independently authorized regular-append capacity, not a claim that disk is full or a proof of global absence. An earlier writer limit, missing authority, unknown contact or failed durable step still returns failure and keeps the attempt consumed/poisoned.

## Original identities, bounds and recovery

`nativeLedgerSpoolCore/v2` is the minimal explicit acyclic storage successor. Its identity is `hash_domain_frames(apiVersion, [canonical core])`. The storage object hash, retrieval ID/proof and full stored original derive from that retained core; the final signed receipt covers all returned references and its complete actual event/head fields. There is no receipt self-reference and no guessed final digest. `nativeSpoolAllocation/v2` adds the exact signed capacity decision. Existing allocation/preparation/storage/completion signature domains remain unchanged because their full canonical payloads bind the explicit successor markers and all added fields; cold grant domains are independently versioned.

The core remains at most 512 KiB and the **complete** endpoint frame at most 8 MiB. Existing storage limits remain 128 objects/32 MiB, DRS 256 records/64 MiB, Current 128 records/64 MiB; opening, operation and sample inventories retain their existing finite bounds. No global cap or proof ceiling increases, no truncation, no retry token and no deadline renewal is introduced. Every phase uses the original operation deadline inside the original assignment/guest/service lifetime.

All old v1/v7 shapes and old signed grant domains remain strict. Old native runtime/v7 retains its separately configured legacy terminal branch; only runtime/v8 selects the actual native terminal map and completion owner. Recovery reads real complete journals under their original scope; it cannot reset an uncertain in-flight operation, reissue a consumed reservation or invent an already-committed terminal. A source-selected new grant does not repair old partial work.

This is source implementation only. It includes no provisioning, key generation, runtime execution, build or test acceptance. The paired [fixed-eight launch, resources, inspection and cleanup](native-shadow-terminal-cohort.md) are connected in the same batch. Independent deployment must still supply genuine keys, signed configuration, original time authority, durable compatible filesystems and the already required complete generation installation. Remaining effect families named above are not completed by this batch.
