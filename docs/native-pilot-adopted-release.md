# Adopted service and bridge assembly

The `.410` slice connects the remaining endpoint producers and the real
ordinary-service publication resources needed after cold adoption. It also
connects the bridge's explicit adopted runtime and descriptor inventory.
These are implementation changes, not a deployed pilot. Source checkpoints
remain **36/46** and independent production acceptance remains **0/6**.

## Connected path

The genuine retained cold core selects the adopted pilot factories. The
ordinary parent uses composite Launch/v7; only DRS and CSA select the explicit
native GuestLaunch/v8 inspected-adoption entrypoint and RuntimeConfig/v12.
The other three ordinary roles keep their established profiles.

Before C9, the actual resource owner retains two additional empty publication
journals and preallocated grant descriptors. Its explicit resources/v2 inventory
has 17 directories. DRS/CSA State/v3 and Wrapper/v3 are produced from those real
preparation/resource originals, an independently signed checkpoint and three
independently supplied anchor signatures. Existing initial profiles do not
accept them by changing a tag.

The runtime names the future grant descriptor; it does not contain a future
grant hash. Generation, dispatch and spool admissions remain present. Complete
native Publication and Retrieval grant inputs and signatures precede either
ordinary root's `nativePublicationServiceGrant/v2`. The actual receiving owner
verifies that root signature and joins it to its retained runtime/history,
generation and native originals before sealing the descriptor. Complete native
admission still happens in the native receivers. Native services persist their own
adoption records; the Python producers never fabricate those records.

The remaining eight native endpoint grant/launch producers use explicit
successor inputs and actual adopted C9/key pairs. All eleven endpoint launch
roles are covered. CommitRequest's companion grant, ledger grant and encrypted
request-commitment authorization remain distinct, independently checked inputs.
Fixed packaged commands check the full public input before selecting a key.

## Bridge and late request acquisition

BridgePreparation/v3 requires the actual eleven-member native peer observation.
The adopted late-current-head path retains the actual new ordinary resources
and verifies the selected wrappers; current-head requests still require
independent decisions rather than deriving approval from an observation.
It does not require DRS/CSA's later guest-launch artifact: that artifact is
published only after the publication grant is sealed. Actual parked owners,
unchanged C9/history/generation originals and pristine retained descriptors
remain mandatory, avoiding a request/grant dependency cycle without permitting
early service release.

Explicit bridge policy/v3 and runtime bundle/v2 compose Runtime/v14 and
Launch/v10. The runtime carries both literal root-signed publication grants and
rechecks their full issuer inputs against the native and ordinary source graph.
Its native 4 MiB aggregate limit is unchanged, despite each publication grant's
3 MiB maximum.

Publication now uses the fixed native listener, not a generic external signer:

The actual driver resource owner enforces this partition and the selected
cohort. Publication's fixed socket and directory are retained and rechecked.
Explicit bridge C9 Input/v3 binds the new inventory; old inputs remain closed.
Installing public runtime files or preparing sockets is not native admission,
service readiness or permission to release the cohort.

## Remaining pilot work

The adopted bridge still needs its complete hot12 measured configuration,
key/closure/transport/launch issuer composition. Its older issuer paths remain
closed; the new transport and runtime do not silently make those paths valid.
The independent supervisor must then compose cold commissioning, actual core
custody, ordinary histories, all endpoint inputs and bridge release/cleanup
through their original deadlines. A coherent local lifecycle and its error
paths remain unverified.

Immutable dependencies, independently operated signing/witness and Nitro/KMS
services, provider/YubiKey integration and complete release acceptance remain
required. This work does not substitute local signing fixtures or root-owned
processes for those independent authorities.
