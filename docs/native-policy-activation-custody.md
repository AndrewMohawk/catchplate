# Native policy activation custody

This is a distinct, explicitly selected native publication operation. It does
not turn a Fleet receipt, a B17 readiness result, key possession, a socket peer
identity, or a successful HTTP response into activation permission. Source is
implemented; build, kernel, filesystem, enclave and end-to-end acceptance have
not been executed.

## Actual ownership and contact

The fixed native guest parent selects `serverware.nativeShadowActivationGuestLaunch/v1`.
Its unchanged `keyAdmission` original admits the C9 delivery, static closure,
encrypted local key inventory, original boot/lifetime, independent time issuer
and external Nitro verifier result. The separate `activation` pin names a
supervisor-signed operational assignment, not a key-admission alias. It commits
the exact guest13, assignment/key-authorization roots, CP authority original,
generation publication, initial journal SHA, current checkpoint and unchanged
signed window. The actual assigned `CustodyActivationPublication` private key
stays in the final role; no raw-key or generic-signing RPC exists.

The signed C9 activation inventory is exactly `activation-channel` and
`activation-journal`, occupying its source-selected FD6..69 positions. The
channel is an actual connected AF_UNIX SEQPACKET socket. This profile carries
public signature-authenticated bytes and intentionally makes no confidentiality
or generic inspected-peer claim. Existing retrieval inspector profiles remain
unchanged. Parent PIDFD, private FD3 and the original absolute watchdog stay
owned throughout acquisition, service construction, publication and cleanup.

The native gate explicitly selects nested `serverware.nativeShadowConfiguration/v3`
in outer v15 or later. Old outer v1-v14 and nested v1/v2 bytes do not select the
new path. `nativeActivation` admits a separately protected authority original
and the actual channel at FD70 under the same root `Prepared`; both originals
survive the permanent serving drop and are bound to the same serving owner.
There is no path reopen after drop. The other endpoint must be handed to the
actual native guest through its signed C9 inventory, not reconstructed from
the channel stat pin.

The authenticated management route is
`POST /v1/policy-shadow/native-activations`. Its exact5 request contains raw
canonical ASCII PREPARE request/response originals; the entire request is at
most 8 MiB. Gate admission requires the genuine retained generation publication
and the opaque consumed completion previously returned to its actual readiness
exporter. Caller-uploaded readiness or a recovered historical observation cannot
seed that owner. A fully sealed zero-link memfd carries the original request;
one fixed control frame carries its SHA, size and once-derived original deadline.
Only one contact is allowed, including uncertainty. A reply is canonical public
receipt JSON (at most 32 KiB) with no descriptors; it is independently verified at the gate.

## READY, approval, currentness and effect

The separate CP producer supplies a native READY sidecar and its own protected
`policy_native_canary_heads` head, retaining the genuine legacy sealing
predecessor without fabricating a Fleet-signed revision. It supplies a currently authorized
hardware requester, a distinct currently authorized hardware approver, and an
actual one-use consume transaction. The native verifier authenticates the full
root-signed CP v6 configuration and its separate planner/verifier/witness keys;
the PREPARE response purpose is
`serverware.policyAuthorityNativeActivationRuntimeResponse/v1`.

`activationOriginals` is exact5: signed measured plan, executor completion,
witness request, witness response and `nativeEffectHoldOriginal`, all raw ASCII.
The verifier binds exact source request/manifest, signed assertion and complete
authorization projection; recomputes SQL radix memberships and the full root
delta; checks the actual approved-to-consumed row, credential-counter/challenge
CAS, READY and preparation originals; and requires the same committed hold
mutation. The hold is `policy_native_activation_holds`, PK `scope`, with fixed
scope `native-policy-publication`. Its source-owned guard excludes conflicting
controlled business/authorization mutations at both real writer effect paths.
Expiry or loss of an acknowledgement does not release it. Only the exact owning
receipt bookkeeping and finalization may settle it. A signed old root snapshot
without that actual protected guard is insufficient deployment authority.

Local custody and CP checkpoints remain distinct owners. No CP `asOf` timestamp
is relabelled as local key trust. The local original interval must fit completely
inside assignment, operational grant and prepared expiry: not-before uses the
earliest time and expiry uses the latest, without midpoint conversion or renewal.

The journal is a retained final-role UID:GID 0700 directory, with existing empty
0600 `activation.lock` and independently pinned 0400 `publication.json` (one link).
The same retained writable local ext4, XFS or Btrfs filesystem is required;
tmpfs, RAM/overlay and network filesystems are not durability substitutes.
This source filter and successful fsync do not prove deployment block backing
or power-loss behavior; those remain runtime/storage acceptance gates.
The initial exact7 state names the real assignment/generation/original publication
tuple and has null predecessor/prepared fields. Absence never creates genesis.
`publication.next`, `activation-request.json` and `activation-receipt.json` must
not already exist. The exclusive original lock is retained through emission.

For the one operation, the service durably creates the exact request claim;
writes, fsyncs and reads back the next state; performs the exact current-state
CAS under the held lock using rename; fsyncs the directory and reads back the
new named original; then signs the distinct receipt17. It also fsyncs and reads
back that receipt before sending it. The receipt commits both tuples, request,
prepared original, durable state SHA, trust checkpoint and entire observed time
interval. It is not the old Fleet activation receipt23, a generic Persistence
proof, a CP-finalized high-water, or a mutation of the gate's immutable policy.

## Provisioning and unresolved outcomes

`serverware.native_policy_activation_inputs.ActivationInputs.prepare` is the
purpose-fixed launch-input producer. Under the unchanged original BOOTTIME
startup deadline it creates an actual socket pair and a fresh `journal` beneath
the existing protected root:root 0711 directory
`/var/lib/serverware/native-policy-activation`. It writes and fsyncs the independently
supplied and pinned initial publication7, creates the real lock, assigns the
exact final UID/GID, and retains process-start/boot/file/socket originals.
It refuses a preexisting journal; failure never cleans up or reuses an unknown
one. `gate_channel()` and `activation()` are observations of those originals,
not constructors from invented inodes.

The independent operator approves the exact C9 payload using `sign_delivery`
with its existing C9 authority key, then calls `sign_service_grant` with the
separately pinned verifier-v2 full18/local-key authorizations and actual existing
supervisor key. Grant authoring checks that actual signed C9 SHA and observed
initial state. It does not mint key authority. `take_for_launch` transfers one
CLOEXEC duplicate set: gate FD70 and service FD6/7, to their distinct actual
supervised processes. It performs no exec or readiness claim. The operator must
close the preparation after this handoff and retain the actual parent lifetimes;
no later effect permits calling the fresh-preparation check again.

Independent provisioning of the initial publication tuple, signed C9/grant
approval, fixed launch originals and CP/guest key authority remains required.
No source path generates supervisor/verifier trust or self-approves keys. The schema is
`native-policy-activation-custody.v1.schema.json`; signedEnvelope framing is
`serverware.signedEnvelope/v1`, NUL, purpose domain, NUL,
`serverware.canonicalJson/ascii-integer-v1`, NUL, full canonical payload.

Any partial journal write, failed readback, lost reply or expired interval is an
unresolved effect, never retry permission. This initial owner is fresh-only and
does not delete files, reset the CP hold, infer no effect from absence, or offer
a recovery write. A separately authorized read-only recovery/settlement path
and original CP audit/finalization are required to resolve uncertainty. Generic
receipt/proof endpoints, all remaining bridge service joins, immutable native
active-policy startup enrollment and production acceptance remain separate.
