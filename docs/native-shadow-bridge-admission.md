# Native bridge combined admission

This source slice activates the real bridge-native configuration through one
retained key/NSM owner. It does not reconstruct a native owner from a signed
hash, and it is not runtime or pilot verification.

## Explicit profile and actual caller

Driver bootstrap configuration/v3 selects continuation preparation/v2 and
requires independently signed scope/v3. The full phase-two original, real
driver observation, actual C9/runtime, descriptor inventory, closure/v2 and
original startup/lifetime remain bound. `OperationalInputs.prepare` and
`DriverBootstrap.continue_scope` are the real retained input/one-send callers.
Old bootstrap v1/v2 remain on their exact prior retention/context paths.

The new independently assigned `nativeShadowBridgeAdmissionAssignment/v1`
adds `productionConfigurationBindingSha256` to the old closed admission field
inventory and has purpose `native-shadow-context-and-production-admission`.
Its separate signature domain is
`serverware.nativeShadowBridgeAdmissionAssignment.signature/v1`. The actual
native configuration factory provides that binding; a request cannot provide
an activated configuration or substitute its own context. The same current
supervisor-role assignment, full key inventory, independence, revocation and
freshness checks still run before encrypted keys are admitted.

The real continuation calls `bind_bridge_admission` on the existing prepared
key owner, then `admit_external`. The new statement retains the complete native
context and adds the actual configuration binding. Its possession domain is
`serverware.nativeShadowBridgeAdmissionPossession.signature/v1`. The fixed NSM
prefix is `serverware/native-shadow-bridge-admission-evidence/v1` plus NUL,
followed by the four original 32-byte statement/full-key/local-key/possession
hashes. This consumes the SAME irreversible key-quote latch; it cannot follow
either old quote purpose or retry a failed attempt. There is no second KMS
contact, key owner, role-key generation, reset, or generic signing RPC.

## Genuine independent verifier and activation

The actual external verifier selects configuration/v3 from its retained root
original. `native_shadow_bridge_admission_profile` verifies the complete
independent key and combined-purpose grants, closed expected scope, full
18-role inventory and exact context. `native_shadow_bridge_admission_verifier`
checks genuine original Nitro COSE, certificate chain, PCR/module/image pins,
challenge, local possession signatures, application denial inventory and
original time/deadline bounds.

Only after those checks, the actual separately assigned verifier key emits:

- A context/config result using
  `serverware.nativeShadowBridgeContextResult.signature/v1`.
- The genuine full production result using unchanged
  `serverware.policyShadowCustodyAttestationVerifier/v1`.

The closed combined envelope retains both complete canonical originals. The
same quote, measurement, endorsement, collateral, current checkpoint, full key
root, signer and validity interval must match across them. The Rust consumer
independently verifies both signatures and the retained actual context and
configuration before `activate_with_verified_attestation`. It never converts
a context signature into a production signature or synthesizes VerifiedResult.
The packaged fixed external runtime includes the new producer; old verifier
configuration/v1 and /v2, evidence/result domains and software trust reporting
remain unchanged. No software verifier is labeled an NSM signer.

The actual native proof bridge retains the activated owner. Its constructor
requires the real generation coordinator and exact production protocol;
generation Recover/Prepare checks compare the request to the actual activated
assignment/configuration, driver/descriptors and current checkpoint before
contact. Commit/Abort retain the real exact preparation/journal chain. Existing
bootstrap and key-owner checks revalidate native admission throughout serving.

## Limits and concrete remaining facade boundary

All old transport ceilings remain: 128 KiB evidence, 32 KiB complete verifier
response, 512 KiB protected verifier policy, one original <=30-second startup
window, and unchanged retained child lifetime. Overflow or uncertainty cannot
renew contact authority. Independent deployment still provisions every actual
authority, image, device, signed policy, sealed key and service resource.

The external gate's `install_retained_generation` currently constructs a
trusted-host configuration through `ProductionProcessConfigV4`; it does not
receive this bridge's live native closure owner. That is a separate concrete
receiving-owner/facade connection, NOT solved by exporting the native Arc as
JSON. This slice supplies real bridge-native activation and actual generation
guards, not a complete external gate facade or installed-generation claim.
The measured bootstrap descriptor inventory is also not a complete operational
settlement/reaper census. Those real owners remain required.

No builds, tests, project parser execution, runtime launch, signing,
provisioning or cloud/provider calls were performed while authoring.
