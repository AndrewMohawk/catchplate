# Native driver operational continuation

This is a source-only intermediate connection, not a tested pilot or full native
configuration activation. Bootstrap v1 and closure v1 stay strict and unchanged.

## Explicit acyclic choice

The old closure pins `runtime.json`; an operational bridge runtime pins the five
generation grants, and those grants pin a configuration containing that closure.
This forms a cycle. Closure v2 (`measured-bootstrap-late-runtime-static-amd64-v1`)
instead pins the immutable **bootstrap** image/runtime/filter. In that version
only, manifest `runtimeConfigurationSha256` means the image bootstrap runtime.
The distinct closure-assignment v2 signature still covers the entire actual C9
Guest binding, including full operational runtime/delivery hashes, and the
current independently verified assignment/checkpoint. Nothing is removed from a
signature or relabeled as approved from a locally computed hash.

The manifest uses existing `hash_domain_frames` with domain
`serverware.nativeCustodyExecutionClosure/v2` over the same ordered construction
tuple excluding its own digest. Closure authorization uses existing
`signature_preimage` with `serverware.nativeCustodyClosureAssignment.signature/v2`.
The real assigned `CustodySupervisorCapability` key, material/SPKI independence,
current trust, revocation and full validity interval remain mandatory.

## Actual caller and ownership

1. `DriverBootstrap.start()` cold-selects configuration/v2. Its exact signed
   original window remains at most 30 seconds. The actual child opens time NSM,
   key NSM and one fixed KMS-helper mechanism while root, then performs the real
   image switch/drop/filter and publishes the actual measured driver observation.
   No role key, ciphertext unwrap, business contact or quote is consumed here.
2. `OperationalInputs.prepare(driver, launch_pin=..., activation_fds=...,
   production=...)` opens and retains real protected public files, opens but
   **does not read** credential contents, and duplicates actual C9 activation
   FDs from their existing resource owners. Its `operation_original()` is data
   for the separate independent phase-two signer, not an authority verdict.
3. The independently supplied scope/v2 signs the entire original observation,
   unchanged startup/lifetime, public bundle, exact descriptor inventory,
   selected launch and native configuration inputs. The Python
   `driver.continue_scope(inputs=..., signed_scope_original=...,
   public_originals=...)` sends it once. No keys/signatures are generated by
   this producer. An attempted send/unknown reply cannot be retried.
4. The actual root supervisor independently verifies that scope and C9, opens
   each protected path and compares its real retained inode and bytes, validates
   the full C9 inventory, and creates the genuine fixed proof-client Inspector.
   It forwards the exact originals plus that newly created private inspector
   channel to the same final-UID child, and services real inspection requests.
   The public caller cannot supply an inspector verdict or channel.
5. The child consumes the measured `Prepared`/driver/phase-two owners together.
   It adopts actual C9 files and activations under a source-private retained
   owner; it does not weaken root-only legacy C9 admission or reopen paths after
   drop. It performs the real NSM time exchange, assignment/current trust checks,
   closure-v2 authorization and exact retained image/filter checks. It invokes
   `from_native_closure_with_settlement_authority` with the actual driver owner
   and compares the independently pinned semantic configuration binding.
6. One existing encrypted-key/KMS owner then performs real
   `bind_admission` -> `admit_external` with its genuine native context and NSM
   quote. Actual `proof_client::Prepared::open_late` -> `AdmittedGuest::hold` ->
   `run_production_rpc_service_native_proofs` connects the inspected clients and
   constructs the existing bridge. No duplicate key owner, second KMS contact,
   reset NSM state or fabricated verifier result is introduced.

The parent/child original kernel startup timers remain armed throughout this
sequence. Only the real completed bridge constructor sends the exact constructed
observation and disarms startup; the original absolute lifetime timers stay
armed. Failure/unknown outcomes retain descriptors, helper and process ownership
until actual same-child exit/cleanup. Existing inherited parent-death safeguards
and actual PIDFD/start/executable/cgroup/filter checks remain in force.

## Closed bounds and deployment boundary

The new child transfer is bounded to 96 FDs: at most 94 signed descriptor entries,
one sealed <=1 MiB public bundle, and one source-created inspector channel. The
old endpoint framing is unchanged. Scope remains <=32 KiB; inner runtime/C9/grant
originals remain <=64 KiB; credential count/total and all production operation
limits remain unchanged. Overflow refuses before native key/business effects.

Independent deployment must still supply the bootstrap/phase-two/C9/assignment/
closure/key/time/verifier authorities and their genuine signed originals,
actual image/filter/device provisioning, and live independently assigned service
resources. The Python producer opens/retains resources; it does not provision
authorities or fabricate final peer measurements. Real root inspectors continue
to require the final executable/UID/IMA/security-label/cgroup evidence.

## Immediate remaining full-purpose join

The retained native configuration is **not activated** by the context-only key
admission result. `AdmittedKeys` verifies a native context quote; full
`ProductionCustodyConfiguration` activation requires the distinct full-purpose
TEE-verifier result. One NSM owner intentionally permits one key quote, so
duplicating KMS/key owners or resetting quote state is not a solution.

The immediate next implementation is an explicitly admitted combined single-
quote profile with a genuine external verifier producer, or an equally strict
full-configuration bridge adapter that verifies every actual context binding.
No placeholder `VerifiedResult`, trusted-host alias, configuration-ready bit or
activation claim is supplied here. The measured four-descriptor bootstrap
identity is also not a complete operational settlement/reaper census.

No builds, tests, parser execution, runtime launch, signing, provisioning,
provider/cloud calls or pilot verification were performed for this source slice.
