The existing path is unchanged:

`RpcPersistenceVerifier::verify_assignment_bound_immutable_retrieval` → exact v4 request → `ProductionRpcServiceBridgeV4` → `ConcreteFiveV3ProductionAuthoritiesV4::verify_retrieval` → the Retrieval endpoint.

No deserialized wire value becomes `AuthenticatedInheritedSeqpacket` or another verified measurement owner.

## Inspection and endpoint calls

The client sends a closed canonical FD4 request containing only sequence, source-fixed phase, exact frame digest and narrowing original deadline. There is exactly one transferred PIDFD: the actual connection PIDFD for connection/before-send, or the actual response SCM_PIDFD for after-receive/after-verify. The parent already owns the one signed target socket, so there is no target PID/path/socket selector.

The parent authenticates every request's real SCM_CREDENTIALS/SCM_PIDFD against its owned clone child and signed final role. On connection it constructs the existing `AuthenticatedInheritedSeqpacket` over a duplicate of its retained actual socket, then repeats that owner's current executable, PID/start, cgroup and SO_PEERSEC checks around every original target PIDFD join. A blocked response retains the request packet and PIDFD originals through emission. Replies authenticate the actual original root parent, echo the exact request digest, match the signed peer measurement and return no descriptors. No same-UID, dumpable, missing-PIDFD or root-serving fallback exists.

Before every send, after every response receive, and again after the unchanged cryptographic reply verification, the client performs the corresponding inspection with the exact original bytes/PIDFD. Wrong ancillary cardinality, peer drift, process exit, unknown messages, clock expiry or inspection failure cannot produce a verified result. The inspection channel is serialized and sequences cannot be renewed. It is signature-independent process evidence, not an alternative signing authority.

The root launch/lifetime parent is the explicit privileged inspection TCB; this does not claim a newly seccomp-confined inspector. No new serving capability or supplementary group is added. Its private API exposes no memory, arbitrary read, ptrace, exec or network operation.

## Genuine lifetime and bridge construction

The native guest retains its actual admission, keys, time interval, closure, launch originals and original C9 owner through the real bridge workers. Bootstrap checks on incoming jobs and outgoing responses use that owner, not a caller-ready flag. The original absolute lifetime timer remains armed; the existing startup timer is disarmed only when the existing complete bridge constructor has authenticated its real dependencies, recovered its real journal and accepted its required facade sessions. No FD3 readiness notice or native driver/proof-scope success is emitted.

Timer storage is the actual kernel-created opaque handle plus its creating process and original deadline, shared only through source ownership; no public scalar/deadline timer constructor was added. In this new threaded profile, every thread checks that same kernel timer's remaining interval against the original absolute deadline. Its independently admitted BPF must permit this actual timer_gettime call and the existing bridge's thread syscalls; the old profiles' check path does not gain this syscall requirement. PDEATHSIG is checked on the actual initial thread, not falsely asserted as inherited by later worker threads. Those workers still retain the process-wide SIGKILL timer and genuine C9 parent channel/PIDFD checks. Parent cleanup still kills/reaps the same real child before releasing its image.

## Remaining completion boundary

This connects the native retrieval client to the existing real bridge factory and signed-response verifier. It does not remove the five existing service dependencies, ten signer endpoints, other three proof endpoints, journal/recovery requirements or genuine production driver/reaper/settlement ownership. Their absence still blocks bridge construction. Native key admission is not converted into those authorities.

A coherent outer launcher must still create and independently assign both real processes, provide the actual client socket/directory and all other signed activation originals, and admit dynamic peer identities without predicted PID/inode values. The server's separate operational grant/fs-verity object producer remains required. No public object/grant, inspection reply or control-plane observation is full bridge readiness. First build, kernel support and complete credential/runtime acceptance remain unverified.
