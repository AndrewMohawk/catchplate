# External native-shadow verifier root ownership

This source slice prepares and retains the external verifier's immutable runtime and mount root. The [fixed supervisor](native-shadow-verifier-supervisor.md) now consumes that actual owner; the owner itself is not a result transport, watchdog, verifier-key provisioner, or native-custody admission. It does not run inside or borrow authority from the claimant enclave. Builds, kernel support, runtime behavior, and production acceptance remain unverified.

## Protected inputs and original interval

The independently provisioned `/etc/catchplate/native-shadow-verifier-launch.json` is an exact three-field `catchplate.nativeShadowVerifierLaunch/v1` document: `apiVersion`, `runtimeImage`, and `verifierConfigurationSha256`. Its paired schema is [native-shadow-verifier-launch.v1.schema.json](../schemas/native-shadow-verifier-launch.v1.schema.json). The retained launch is canonical ASCII JSON, at most 16 KiB, a root:root 0400 regular file with one link, reached through protected non-symlink ancestors.

`runtimeImage` is the exact five-field output selection from the separate [verifier runtime packager](native-shadow-verifier-runtime.md): `profile`, `imagePath`, `imageSha256`, `interpreterSha256`, and `entrypointSha256`. The profile is `sealed-memfd-squashfs-v1`, and the fixed path is `/opt/catchplate/native-shadow-verifier-runtime.squashfs`, at most 512 MiB. The fixed interpreter is `/usr/local/bin/python3.11`; the sole script is `/opt/catchplate/scripts/verify_native_shadow_custody.py`. These independently admitted pins are not synthesized from a directory listing or accepted as proof of verifier authority.

The launch hash pins the exact original `/etc/catchplate/native-shadow-nitro-verifier.json`, retained under the same root:root 0400, one-link protections and a 512 KiB bound. That existing configuration supplies the final nonroot UID/GID, actual external boot ID and time-namespace identity, and original absolute `issuedAtBoottimeNs`/`deadlineBoottimeNs` interval of at most 30 seconds. Preparation only consumes this interval; it never starts another clock or cleanup allowance. The final identity must differ from the claimant identity and reserved native worker identities. Full authorization, PKI/PCR, checkpoint/revocation, key association, evidence, and signed-result semantics remain the existing Python verifier's responsibility, not a claim made by the Rust mount owner.

## Actual retained root

`native_shadow_verifier_runtime_v1::RuntimeAdmission::open()` requires a genuine single-threaded root supervisor. It retains that process's PIDFD/start time, real/effective/saved root identity, boot, PID namespace and time namespace, plus the actual configuration descriptors and bytes. The supervisor arms its kernel deadline signal from this same admission before `prepare(self)` consumes it. Preparation creates a private mount namespace and a fresh root-only workspace under `/run/catchplate-native-shadow-verifier`; it neither reuses nor replaces a job directory.

The additive `ExternalShadowVerifier` image purpose uses the existing complete-image pin, sealed memfd, read-only exact loop-backing, SquashFS, and interpreter/script checks. It does not alter the broker, role provisioner, or shadow claimant purposes. The actual detached image root is attached to the fresh job root. The same held configuration inode that will be FD3 is bound over the image's fixed empty 0400 placeholder, then restricted read-only/nosuid/nodev/noexec. A genuine read-only/nosuid/nodev/noexec procfs is mounted at the fixed empty `/proc` target. The zero-byte image placeholder itself cannot pass configuration admission. Mount IDs, inode/device associations, read-only flags, source-image/seal/loop ownership and executable originals remain held and checked, not inferred from a successful mount call.

The owner makes no final UID drop: the [fixed child](native-shadow-verifier-child.md) switches into this root, installs the separately admitted original FD4 key and FD5 evidence, closes inherited host/root descriptors at exec, performs the permanent identity/capability/group drop, and executes only the fixed interpreter/script. The policy's original time namespace and boot survive those actions. The runtime's checks require the root supervisor to retain its own identity through cleanup. The supervisor's absolute kernel timer is separate from these synchronous original checks; the checks alone do not interrupt blocked kernel calls.

The running owner binds one actual child, not an arbitrary descendant-process closure. The fixed supervisor must prevent untracked child creation and descriptor escape, or separately retain and settle those actual owners; reaping this PIDFD alone is not proof that an uncontrolled descendant has stopped using the root.

## Private supervisor interface

All owner types and methods are crate-private and non-serializable. No public descriptor constructor, command, arbitrary path, sign, quote, or key-return interface exists.

- `RuntimeAdmission::open()` / `check()` retain and recheck the public originals. Its UID/GID and original interval getters support input binding and timer arming; `prepare(self)` consumes that actual admission without accepting a replacement deadline or configuration DTO.
- `PreparedRuntime::check()` rechecks the prepared image/root. `inheritance(&mut self)` is once-only and returns a borrow exposing only `root()`, `interpreter()`, `configuration()`, `uid()`, `gid()`, `issued_boottime_ns()`, and `deadline_boottime_ns()`.
- Immediately after its genuine clone, the fixed supervisor consumes `bind_child(self, OwnedFd, pid)` with its actual clone-created PIDFD and returned PID. Binding verifies the kernel PIDFD identity, real parent/start relation, and `waitid(P_PIDFD, WEXITED|WNOHANG|WNOWAIT)` child ownership. A numeric PID alone cannot construct a running owner.
- `RunningRuntime::check()` requires the same live child and original runtime. `check_after_exit()` instead requires that same child's actual terminal kernel evidence and all runtime originals while the original interval is still live. Neither method accepts an exit DTO or caller boolean.
- `child_pidfd()` is a borrow of the actual retained PIDFD for the supervisor's stop/poll operations; it asserts neither liveness nor successful verification.
- `retire(self)` obtains matching terminal evidence, actually reaps through the same PIDFD, then detaches only the retained exact mounts, removes only its own empty job paths and restores the original mount namespace. Its private `Retired::code()` / `status()` report the kernel result only. Retirement can run after expiry solely for cleanup; it never grants output eligibility or new verification time.
- `BindFailure` and `RetireFailure` retain the entire actual owner. `error()` describes refusal; `into_cleanup()` returns that retained `RunningRuntime` for actual stop/reap or cleanup retry. Partial cleanup records completed steps without choosing replacement pathnames. Missing identity or terminal evidence causes refusal, not an assumed successful cleanup.

Before inheritance, drop attempts only best-effort cleanup of the owner's fresh preparation. At inheritance, automatic mount/namespace teardown is disabled because descriptors may already be in a child. After that point the supervisor must retain the owner through actual child stop and explicit retirement; dropping it cannot infer death or authorize detachment. If clone fails after inheritance, there is intentionally no caller-asserted “no child” cancellation capability: the fixed supervisor must fail closed and exit, rather than reuse the process/root or fabricate a child. Kernel namespace teardown then handles that process lifetime; private empty workspace remnants may remain and no explicit cleanup success is claimed.

The fixed supervisor connects bounded stdout custody, original FD4/5 checks, `check_after_exit()`, successful exact retirement with `CLD_EXITED` and status 0, and final original input/time checks. Output itself remains subject to independent signed-result verification. Actual builds/kernel validation, deployment/install provisioning, bounded external service launch, result transport and end-to-end native shadow admission remain required work.
