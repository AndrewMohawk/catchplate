# Cold OAuth application ownership

This is a source-only O01 admission checkpoint, not a working production OAuth lifecycle or a tested pilot. The actual OAuth consumers now retain a separately admitted application association. The enrolled production profile deliberately refuses before issuing a consent URL, exchanging a code, refreshing/revoking provider material, or entering the legacy credential mutation wrappers until the purpose-controlled lifecycle writer is connected. Unconfigured `dev`, `development`, `local`, and `test` retain the explicit old environment-configured path. Any OAuth startup namespace mention selects strict admission; malformed or expired admission never falls back.

## Independent enrollment authority

`oauth_application_owner.py` admits the closed [enrollment/startup profiles](../schemas/oauth-application-enrollment.v1.schema.json). The administrative producer `sign_enrollment` signs `serverware.oauthApplicationEnrollment/v1`, NUL, and the exact canonical ASCII payload (`ensure_ascii`, sorted compact JSON, no LF). Its private signing key is an administrative input, not a runtime credential or proof of a root assignment. Deployment administration must separately authorize this root for OAuth enrollment and assign the provider-family namespace and generation. A client ID, Google project guess, runtime custody signature, or self-described metadata is not that assignment.

Fixed root delivery reads `/run/serverware/authority-trust/oauth-applications.json`, the independently provisioned `/run/serverware/authority-trust/oauth-application-root-public-key`, and selected `/run/secrets/serverware-oauth-google-client` or `/run/secrets/serverware-oauth-x-client`. There is no caller-selected source path. The private originals require root ownership and mode `0400`; the delivery seam seals the bounded originals into inherited descriptors. The startup configuration pins the exact root bytes and descriptor roles, and the OAuth root SPKI must differ from the custody runtime root. The existing genuine runtime admission authenticates startup delivery and its exact inherited descriptor inventory separately; it does not confer OAuth signing authority on its own root.

The startup configuration is exact six fields and at most 64 KiB. It contains zero to two unique providers, each with an enrollment and separate client-material descriptor. An empty list requires both root fields to be null and disables enrolled OAuth. Existing fixed-role deployments must provision this configuration and its exact inherited inventory explicitly, even when selecting the empty list; there is no automatic upgrade. Client originals are exact five fields, canonical ASCII at most 32 KiB; the public root original is at most 4 KiB. The owner verifies the purpose signature before parsing private client contents, exact source revision/current configuration digest, original issue/expiry interval, client-material hash, client ID and redirect. It retains and rechecks the original descriptors, seals, file identities and bytes, actual custody owner, process identity, environment selection and original interval. The source does not claim Python secret-memory erasure.

## Actual consumer joins

The signed enrollment binds deployment, application, provider, independently assigned provider-family namespace/generation, exact client/redirect, and the source endpoint/flow configuration hash. Provider configuration covers authorization/token/revocation/identity URLs, token authentication, default scopes, authorization parameters and response-scope behavior. A configured but unenrolled provider is disabled, not recovered from environment variables.

The source-selected association is propagated through actual consent state, code-exchange output, encrypted token/revocation material, credential metadata and exact activation review. The review digest therefore binds the application as well as the verified provider account and token original. Callback and refresh retain the same private operation through the app/database boundary; serialized association data cannot create that owner. Reconnect and version-CAS refresh compare the prior association, and pending activation rechecks the stored review against current metadata and the current cold owner. Lease-side managed OAuth use checks the association even when a refresh is not yet due.

Admission and each operation have an original wall/monotonic allowance of at most 30 seconds, further shortened by the admitted custody maximum, original custody receipt expiry and signed enrollment expiry. The long-lived owner maps the original absolute expiry to a monotonic deadline once and rejects backwards wall/monotonic observations. HTTP timeouts are clipped to the operation's remaining allowance. No callback, persistence helper or response object renews that retained operation. Issued token bytes are retained for revocation before a post-contact owner/deadline check can fail. The browser state keeps its own existing expiry; a later callback is a distinct bounded operation but must still match the same original enrollment and current interval.

## Atomic writer boundary and next implementation

The existing activation transaction atomically consumes the exact approval, writes/replaces the credential, removes the pending row and appends audit evidence. Its production approval/WebAuthn/audit tables are not writable by the generic runtime. Consuming approval through a controlled writer and then performing independent runtime credential DML would lose that atomicity. This checkpoint therefore has a temporary explicit pre-contact and mutation refusal, not a synthetic success result or broader SQL grant.

The [purpose-bound new-credential/no-setup activation](oauth-atomic-activation-authority.md) now connects that entire transaction to the controlled writer with exact admitted application, pending material, requester, distinct approver, original expiry and current role/authenticator bindings. Its [public caller](oauth-controlled-activation.md) does not lift the consent/exchange refusal or create a pending credential. Pending staging, reconnect, refresh, revocation retention and their setup/audit joins must follow before removing the corresponding entry refusal. This is unfinished implementation, not an accepted terminal product state. The new protected setup/generation roots also require controlled successors for their documented legacy direct-write callers; those are required follow-on work, not permanently disabled functionality.

O01 remains partial. No shared atomic fenced subject coordinator or cross-deployment reservation is implemented here; the existing Google collision guard remains database-local. Administrative namespace assignment alone does not coordinate external applications or prove duplicate issuance impossible. The provider subject is still learned after exchange, so pre-subject issuance ownership requires its own design and real consumer. O02 measured provider-exchange custody is separate. Enrollment/key/configuration renewal or migration is not inferred: changing the original enrollment invalidates outstanding associations until an explicit transition exists. No deployment, provider contact, build, test or runtime verification was performed for this source checkpoint.
