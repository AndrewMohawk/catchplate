# Atomic OAuth activation authority

This source connects one operation: a retained enrolled OAuth pending original becomes a **new credential, with no setup-session or reconnect transition**, only through a fresh purpose-bound physical-authenticator ceremony and one atomic controlled-writer transaction. It is source-only, unbuilt, unexecuted and unprovisioned; it is not O01 completion or pilot validation.

The public caller is described in [controlled OAuth activation](oauth-controlled-activation.md); application ownership is described in [OAuth application ownership](oauth-application-ownership.md). [The authority schema](../schemas/oauth-activation-authority.v1.schema.json) is data validation, not a source of authority.

## Independent cold authority and originals

The actual signed measured authority configuration may include `oauthActivationPolicy`, exact five fields: `schema`, `enrollmentRootPublicKeyBase64Url`, `enrollmentRootSpkiSha256`, `controlPlaneConfigurationDigest`, `deploymentId`. Its schema is `catchplate.oauthActivationAuthorityPolicy/v1`. Enabling any of the three new operations requires this pin. The enrollment key must match its SPKI digest and differ from the authority configuration root and role signing/response keys. No HTTP caller supplies this trust root.

The verifier and planner independently authenticate the exact canonical signed `catchplate.oauthApplicationEnrollment/v1` original, under their own admitted configuration, before assertion issuance or planner SQL/persisted-plan lookup. The signature is Ed25519 over the payload schema, NUL, and sorted compact `ensure_ascii` JSON payload. Enrollment source revision, original interval, deployment and control-plane configuration digest must agree. The latter is the genuine retained control-plane custody configuration digest, not the OAuth startup file hash.

The client retains its real `OAuthApplicationOwner` operation, exact signed enrollment, custody client and original narrowed deadline. The request carries only exact binding digests and the signed enrollment—not pending ciphertext, a root selected by the caller, a success verdict or a renewed lifetime. The selected protected pending row is committed as all 26 actual columns with exact SQL scalar types and sorted compact ASCII JSON, bounded to 1 MiB. Only its digest crosses the public authority request. Metadata and review must agree with the signed application association; the original existing pending review/token `payload_digest` is preserved, not replaced by a digest of the new binding.

## Ceremony and indivisible transition

The three operations are `oauth-activation-approval.request`, `oauth-activation-approval.decide`, and `oauth.pending.activate`. Each has the same eight raw arguments: `action`, `resource_id`, `payload_digest`, `actor_id`, `request`, `approval_id`, `credential_policy`, `enrollment_original`. The action is only `credential.oauth.activate`. Request binding has `pendingCredentialId`, `pendingRowSha256`, `enrollmentSha256`, `payloadDigest`; all are exact original associations. The request phase alone has null `approval_id`.

Requester and distinct approver both need the literal current `credential_owner` role; an admin-only shortcut is not accepted. Every phase uses genuine raw assertion verification, current authenticator key/counter, challenge, RP/origin, user presence/verification, current hardware/attestation policy and published trust/withdrawal originals. The fixed credential policy permits only hardware/yubikey classes. An assertion-receipt signature alone is not proof of physical trust. Approver notes are null. Old generic approval provenance cannot be relabeled as `catchplate.oauthActivationApprovalProvenance/v1`.

Approval expiry is at most five minutes and clipped downward to pending and enrollment expiry; each actual operation retains the caller's original deadline. The activation transaction atomically consumes the approved row, updates requester assertion counter/challenge, inserts the existing ciphertext under the same pending ID and version 1, inserts the previously absent generation head, deletes the exact pending row, and appends the authority audit. There is no separate consume, callback, decrypt/re-encrypt, provider contact, setup mutation or revocation effect. Signed result6 (request/decide) or result7 (activation) includes the exact public approval, and only activation includes the existing secret-free credential projection. Uncertain or replayed operations do not acquire another execution allowance.

## Complete populations and maintained roots

Before the kernel, the real planner selects bounded complete populations for `credentials`, `pending_oauth_credentials` and `setup_sessions`. It reconstructs each entire radix tree from original rows using the existing SQL-matching authenticated key/row/leaf/node recipes and empty subtrees, and requires equality with the same transaction's before-root. Membership proofs, SQL counts and `leafCount` are not substituted for completeness. Omitted rows change that root. The surrounding executor retains its ordinary current-root/fence checks through atomic commit. Work is charged to the existing invocation ledger and its original deadline.

This first profile refuses any table with more than 64 rows, including historical/terminal rows. That is a temporary capacity limitation requiring larger bounded acquisition—not a claim that populations are always small. Google checks all local credential and pending identities; ambiguous missing historical client IDs collide for the same subject. It does not prove cross-deployment provider ownership. Any setup session referencing the pending ID refuses this new-only operation.

`credential_generations` and `setup_sessions` now join the actual protected schema/root inventory and source primary-key contracts, not merely a private lookup dictionary. The standard source-derived query manifests, authenticated triggers and owner/reader ACL admission include them. Runtime DML is not granted to work around missing lifecycle operations.

The concrete legacy direct-write owners affected by those ACLs are `db._expire_and_prune_setup_sessions` (expiry and pruning, also reached by convenience readers), `create_setup_session`, and `transition_setup_session` (including callback/pending/activation setup bindings). Generation writers are `_record_credential_generation` / `_next_credential_generation`, reached by `quarantine_google_oauth_grant_family`, `create_credential`, legacy `activate_pending_oauth_credential` (new and reconnect), `reconnect_oauth_credential`, `upsert_credential_with_id`, `update_credential`, and `update_credential_secret_if_version` (including refresh). All need their appropriate controlled successor before production use. `init_db` also performs an owner-only generation backfill; that remains staging/provisioning, not an application-runtime DML fallback or an authorized migration in this slice.

The actual inventory joins are `authority_contract.V9_ADDITIONAL_PROTECTED_TABLES` and `authority_primary_contract.PRIMARY_KEY_COLUMNS`; source-derived operation read/write manifests feed `db`'s `tracked_authenticated_tables`, which installs the real authenticated INSERT/UPDATE/DELETE triggers and before-root records. `authority_store.schema._policy_candidate_authority_schema_tables` and the runtime read-only ACL inventory consume the same protected-table list. This change therefore requires updated admitted schema/ACL originals rather than treating an old deployed schema as compatible.

## Remaining lifecycle and provisioning work

The enrolled profile's general before-contact refusal is not lifted by this operation. Pending staging, provider callback/exchange and O02 measurement, refresh, reconnect, setup-session binding, revocation and cross-deployment coordination still require their actual owners and controlled atomic transitions. Existing direct setup/generation mutation paths must be replaced before their production use; they are not accepted as permanently disabled product functionality. Larger populations need a coherent bounded complete-root acquisition extension. No old-source migration or generic approval fallback is provided.

An actual deployment still needs independent application-root enrollment, signed measured policy, configured operation grants, real custody/verifier/planner/executor services, compatible protected SQL schema/ACLs, current physical-authenticator trust originals, provider registrations/secrets and an authorized runtime-validation phase. None were provisioned or exercised by this source change.
