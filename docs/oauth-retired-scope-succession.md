# Append-only retired-scope succession

This source adds a separately authorized control-plane and protected-writer
path for succeeding a retired OAuth family or an explicitly wider provider
scope. It does not clear a retirement marker, reopen an old currentness epoch,
retry provider contact, or imply global provider-family ownership. Native
historical-material custody, signing, fixed-provider TLS, browser and startup
implementation is a required separate producer join. No build, parser, test,
browser, provider or runtime result is claimed here.

## Independent authority and immutable predecessors

`oauthRetiredScopeSuccessionAuthorization/v1` is signed under a new independent
successor root. The existing signed authority configuration/v6 selects the
separate `oauthRetiredScopeSuccessionPolicy` and exact operations. The policy
retains enrollment and native role-4 verification separately. A controlled
writer receipt admitted as trusted-host-local remains trusted-host-local; it
is not relabeled as native TEE custody evidence.

The authorization names the exact target UUID/version/account/application,
every affected local lineage, each retained material, predecessor row and
journal, the previous provider-head digest, all 28 table roots, requester and
original absolute windows. Same-family continuation cannot silently replace
another family head. Widening to provider scope requires an independently
signed provider-wide external-impact permission and all affected drains.
Local complete inventory is not evidence about other deployments or external
clients. Provider revocation may affect related tokens/grants; token inequality
is not token isolation. Old Google/X cleanup and reconnect grants are not this
purpose.

`oauthApplicationStartup/v5` is an explicit cold selector. It retains the actual
application/enrollment/runtime owners and adds a separately sealed independent
root and authorization inventory at fixed root-delivery paths. v1-v4,
including v4 reconnect, keep their old contracts. No incoming request chooses
an effect root, signer, endpoint, DSN or startup profile. Existing non-successor
token-effect callers refuse an installed succession head rather than using a
bypass boolean. Authenticated current successor associations allow the actual
refresh owner to continue and append the next association atomically with its
new credential/currentness root. Non-target fenced lineages remain fenced.

## Complete bounded acquisition and the final fence

The source-fixed `authority_oauth_retirement_succession_catalog.SNAPSHOT_PARTS`
is the only table/part map. A real requester hardware authorization creates the
one-use journal and exact scope-approval request. Its one live owner then sends
all 28 fixed snapshot operations, once each and only following a definite
acknowledgement. Each immutable slot records the actual admitted complete root,
bounded rows, request digest and original admission expiry. No caller can
choose an alternate table, predicate, sort order or proof primitive.

| Acquisition class | Parts / capacity |
| --- | --- |
| Live graph | credentials, pending, Setup, exchanges, refreshes, work; 16 each |
| Issuance / refresh provenance | initial, Setup, reconnect, succession, refresh custody; 64 each |
| Cleanup provenance | exchange, refresh, pending and capture journals/attempts plus measured cleanup custody; 64 each |
| Immutable retirement history | old family and pending-family markers; combined 32, both complete roots retained |
| Other retained history | provider fences, reconnect authorizations, succession material claims/attempts; 64 each |

The complete source map has 28 parts. Each independently authenticated part is
at most 1 MiB; all retained raw parts together are at most 4 MiB. Both limits
and actual source meters apply before effects. The distinct approver reviews
the original grant and completed acquisition, then uses fresh physical
hardware for the exact scope approval. There is no generic approval conversion.

The original requester may then coordinate real currentness drains for every
still-active affected lineage, using the actual credential/head rows and the
original grant/evidence/request deadlines. Missing or unreachable holders block;
a wait or timeout proves nothing. Historical consumed predecessor barriers are
independently checked as retained facts, never coordinated again or reopened.

Final FENCE is one protected transaction: it compares every required current
table before-root with the original authenticated snapshot root, rechecks the
full graph, original grant, live requester/approver hardware and roles, consumes
the actual newly admitted barriers, fences affected credentials, creates an
immutable scope, and advances the monotonic provider head. A root mismatch
cannot rebase the snapshot or split the fence. All 28 raw tables are not
returned as one oversized proof. The global proof ceiling remains 256;
individual source-selected operation budgets and both real acquisition meters
remain in force. Capacity overflow refuses; there is no truncation, pruning,
archival or migration authority.

The fixed query declarations peak at 150 rows for fresh PREPARE (including its
65-row exchange-history sentinel), 109 for initial authorization, 87 for FENCE
and 70 for a history snapshot. The actual source-owned audit-capacity acquisition
is also charged within the 192-row operation budget. Every SQL read, proof,
retained-root reconstruction and byte encoding keeps its own existing meter;
these declaration counts are not a substitute for measured work or a permission
to skip a member. The global 256-row ceiling is unchanged.

## Retained material and fresh target generation

The complete graph includes initial and Setup captures/pending tokens,
reconnect and succession captures/candidates, refresh-issued/superseded work,
and still-current encrypted credential material. It binds the actual minimal
issued capture separately from normalized pending/candidate token material,
exact envelope/AAD identity, source/custody rows and historical enrollment.
The grant allows at most 16 materials and seven affected lineages. Each X
material can select access and refresh contact (at most 32 attempts total);
Google selects one purpose per material, never assumes family-wide effects are
isolated. Historical exchange origins are complete and bounded, not sampled.

The native owner must independently verify the definite signed FENCE request,
response, authority root/configuration, exact committed journal/scope/currentness
and original grant before handling private material. Each material first needs
its own native INSPECT proof and definite protected MATERIAL-CLAIM. Only that
actual retained claim may precede decryption. A separate CONTACT consumes the
exact token-request commitment once, before provider I/O. If a complete
authenticated accepted prior contact matches, the writer records
`accepted-existing`: the owner must not POST. Rejected, unknown or contact-claimed
history blocks continuation; a new grant, timer or missing acknowledgement does
not convert it into success. FINISH retains actual encrypted TLS response and
transport-derived accepted/rejected/unknown under the original window.

After all materials have genuine accepted evidence, their exact closure digest
binds fresh private state and the new PREPARE/CLAIM/CAPTURE/STAGE chain. The
authorization UUID is the exchange UUID; fresh token sealing uses the existing
target credential UUID and exactly N+1, not the exchange UUID or a new alias.
The provider identity must be the same independently verified account, and the
target's actual enrolled application association remains unchanged. Fresh
candidate review includes scope and material-closure digests. A separate
requester/distinct-approver hardware ceremony precedes activation. Activation
atomically replaces only the target credential, advances the generation,
creates its real new currentness root and appends the authenticated association.
It never mutates the old scope, fence, attempt or old root. Later refresh adds
another authenticated association instead of treating mere association
existence as current authority.

## Actual operator and HTTP flow

The normal portal has a dedicated retired-scope section; it does not reuse the
old reconnect or Setup purpose. All human POSTs require the genuine OIDC
credential-owner role, current cookie identity, exact origin and CSRF token.
Requester and approver must be different real people; each relevant ceremony
uses the actual hardware challenge/verifier/writer path.

1. `POST /api/oauth/succession/inventory` reads cold-admitted requester grants.
2. `GET /api/oauth/succession/{authorizationId}` observes retained rows, complete
   snapshot names, contacts, candidate review and purpose-specific approvals.
3. `POST /api/oauth/succession/ceremony/options` and `/ceremony` carry the closed
   authorization ID, operation and approval ID. The latter additionally carries
   `oauthRetiredScopeSuccessionProfile` + the fresh assertion. The five exact
   operations are authorize, decide, activation-request, activation-decide,
   activate. The assertion is never persisted by the browser.
4. The definite authorize response includes all 28 acquired part names. A lost
   part acknowledgement cannot resume through another HTTP call. Distinct-person
   decide follows only the original completed acquisition.
5. `POST /api/oauth/succession/fence` carries only the authorization ID. The
   actual requester owner consumes retained approval/current hardware evidence,
   drains active holders and attempts FENCE once. Only the definite signed
   response constructs the native intent.
6. Direct native `/oauth/begin#original=<base64url canonical intent>` carries no
   new root or success verdict. The native purpose must independently verify all
   originals, retire selected material, establish closure, then create PKCE and
   fresh machine PREPARE before authorization redirect. No CP draft conversion.
7. After native STAGE, inspect and perform separate candidate approval and
   target activation. Keep nonsecret IDs for read-only uncertainty inspection.

The native machine route is `POST /api/data-plane/oauth-succession`, exact3
`{apiVersion,operation,arguments}`. It requires the actual data-plane transport
token as well as independent purpose proof. Fixed `/original` acquisition is
read-only, exact2 `{apiVersion,authorizationId}`; missing association is unknown,
not no-effect/completion. Signed RECOVER is also observation-only. It has no
processing nonce, contact grant, recovery staging or deadline renewal. No UI or
service path recreates a lost FENCE response or automatically repeats a send.

## Frozen native producer contract (implementation still required)

Actual declarations are in `authority_oauth_retirement_succession.py`,
`authority_oauth_retirement_succession_policy.py`, the record codecs and paired
schemas `oauth-retired-scope-succession.v1.schema.json` and
`native-oauth-retired-scope-succession.v1.schema.json`. Their schema acceptance
does not replace admission. The future helper must remain portable: no import
of the control-plane storage/authority graph in the measured image.

| Original | Closed contract |
| --- | --- |
| Cold native configuration | exact17; own `nativeOAuthSuccessionConfiguration/v1`; current applications plus `historicalApplications`, `successionLimits` |
| Private configure projection | exact19; remove browserVsockPort, add actual identity and ingress leaf certificate/SPKI digests |
| Intent | exact10; old seven scalar fields + authorizationOriginal + scopeRequestOriginal + scopeResponseOriginal |
| Private state | own `nativeOAuthSuccessionState/v1`; old 21 scalar names + `successionBinding` exact8 |
| Native statement | exact24; own phase and schema, authorization SHA, scope-row SHA, required-null-or-material UUID |
| Machine arguments | exact12, including real independent assignment, enrollment, authorization and native proof |
| Kernel result | exact7; actual originals9 + observation6; no copied receipt permission |
| Recovery acquisition | exact9 result including own API and `okForAction:false`; raw canonical ASCII row strings |

Native phases are literal `inspect`, `material-claim`, `contact`, `finish`,
`recover`, `prepare`, `claim`, `capture`, `stage`, `cancel`. There is no draft
alias. The proof operation is `nativeOAuthRetiredScopeSuccession.sign/v1`;
signature domain is the exact statement schema + NUL. NSM nonce is SHA256 of
`serverware/native-oauth-retired-scope-succession-attestation/v1` + NUL + challenge
32 + SHA256(statement) + signature64. Existing native key/boot role-4 evidence
remains genuine and separately bound.

Historical applications are sorted unique by **exact enrollment SHA**; each
closed entry is `{enrollmentSha256,enrollmentRootSpkiSha256,application}`. Current
application duplicates are refused. Assignments are selected by the pair
`(holderId,enrollmentSha256)`, never by provider alone. The native owner must
match the retained signed historical enrollment, independently admitted
historical root/signature, application ciphertext SHA, actual native key/boot,
provider TLS PEM SHA and genuine retained KEK/key. An expired historical
enrollment is provenance only; the new successor authorization supplies effect
permission. Fresh issuance uses only the one current target enrollment.
Unavailable historical keys/material or mismatched bindings must refuse; adding
genuine historical key custody is implementation/provisioning work, not license
to reencrypt as provider validity or substitute a current application.

Bounds are on complete originals, not just one field: native cold configuration
2 MiB; grant128 KiB; each machine argument2 MiB; request3 MiB; canonical kernel
result1 MiB **before commit**; full signed runtime response2.75 MiB; complete HTTP
and helper frames8 MiB; private state64 KiB; encrypted transport record384 KiB;
candidate512 KiB. Raw original arrays remain inside the aggregate result cap.
The nominal material/row counts do not promise all maximum-size combinations
fit. Overflow refuses, and no generic frame is widened. Scope request/response
are base64url in the intent; retained row originals in results are raw ASCII.
All operation/contact/retention/pending windows remain clipped to the original
grant and actual native lifetime; each browser action supplies no new interval.

## Still required / not claimed

The purpose-specific native helper/proof/browser/startup and historical-key
custody join, packaging, integrated builds and end-to-end runtime verification
remain required. Live credential-bound Setup flows are not silently cancelled
or completed by succession; conflicting active sessions refuse and need their
separate authenticated lifecycle successor. Archival, capacity migration,
malformed-history repair, global external-family closure and automatic
non-target reopening are not provided. A fresh-account one-provider pilot may
deliberately exclude retired-scope recovery, but a pilot claiming recovery needs
this full native join and observed execution. This source count is not a time
estimate or production acceptance result.
