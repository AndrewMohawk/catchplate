# Historical activation to current consume inputs

The `.223` source slice connects genuine consume-input production, original-only
receiving and cold worker intake across separately authorized root keys. It
does not enable the public fresh-consume action for historical authority. The
actor's explicit refusal remains; the actual delivery-plan provenance/current
state split, later grant/reserve/SQL/completion and release remain separate work.

## Independent originals

The existing producer and receiver signatures remain unchanged: raw16 activation
evidence, issuer-policy original, old activation-planner original, current root,
and the caller's original work/window/deadline. No admitted result object, posted
key or new descriptor replaces an original.

Issuer-policy v2 is signed by the current root. Its genuine admission supplies
the independently pinned historical root and interval, original caller/grant/
state enrollment digests, and a separately admitted current planner context.
Old activation evidence is authenticated only with that historical root. The
producer joins the actual caller/grant/state enrollment identities and original
plan/caller/grant/reserve intervals before deriving anything. Completion
observations and actual old-token possession are genuinely checked as before.

Fresh output configuration, generation, runtime identities, authentication/trust
policy, age/skew limits and state enrollment come from the current context.
Old and current state enrollments are independently verified under their own
roots and must have equal complete payloads; their signed envelopes need not be
identical. This permits separately authorized root rotation, not invented state
migration. The original acknowledged after-vector and activation provenance
remain bound to the same database/generation. No original delivery timestamp,
TTL, target, token commitment or expiry is renewed.

## Versioned history and planner originals

The new history-custody v7 has the fixed
`bridged-consume-planning-history` purpose at the existing consume planner
process identity. Its current-root signature binds the old planner, exact typed
consume request and immutable issuer-policy original. Its verifier genuinely
re-admits that policy and the historical planner, retaining distinct outer and
historical roots. Ordinary v1–v6 purposes keep their existing schema/signature
domains; v7 cannot become a grant, reservation, SQL or completion purpose.

Consume-planner v3 independently verifies that v7 original, all current static
output fields and the exact policy-derived fresh interval. Old activation
expectations stay bound to the old planner. State enrollment comes from the
current context; resource/key separation still includes historical custody and
both relevant planner/root contexts. Existing planner v2 stays unchanged, and
the historical planner entrypoint does not silently accept v3.

The raw2 receiver repeats actual policy/evidence derivation and compares the
complete independently derived payloads to the genuinely verified signed pair.
The staging receiver separately admits policy and both originals; it does not
claim raw16 possession replay. Private history custody re-authenticates the
fresh outer with the current root and uses only the selected historical root
for old evidence. No old private signing key is introduced.

## Capacity and unfinished boundary

`_cold_derivation_reservation(policy_bytes, activation_bytes)` exposes the same
length-only capture inventory used by derivation. Request bodies add eight
actual raw16 footprints; receiving adds its existing response captures. The
embedded current planner is counted inside the measured policy inventory.
Production additionally reserves signing output before genuine derivation.
Staging keeps the existing fixed v1 reserve and adds measured excess-policy
captures. All remain inside the original 64 MiB ceiling and original ledger;
large otherwise valid policies can be refused rather than opening a new budget.

This is input production/admission and worker intake only. The current
delivery-plan path still couples its old provenance inputs to current state,
so no historical public consume permission is enabled by these new profiles.
The source is unbuilt and unexecuted; no runtime or production acceptance is
claimed.

The subsequent [`.224` protected planning connection](historical-consume-execution.md)
separates old provenance from current state through the actual private planner
and caller preparation. Grant/reserve/SQL/completion bridge profiles remain open,
so the public historical consume execution gate is still closed.
