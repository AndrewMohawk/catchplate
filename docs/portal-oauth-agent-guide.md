# Portal OAuth And Agent Guide

This guide covers the operator path for connecting OAuth-backed services in the Serverware portal and the agent path for using those credentials without direct credential delivery. Serverware still handles plaintext transiently in its trusted injection path. The Rust gate zeroizes its explicitly owned request/header maps, lease material, buffered and streamed body fragments, strict-JSON graphs, serializer output, proof/signing state, custody frames, and attestation-command staging on normal and error exits. Public diagnostics and cleartext telemetry use fixed reason codes plus bounded counts or digests; they do not reflect provider-derived header names, JSON keys, Gmail message IDs, parser values, transport URLs, or header copies. Authorization-bound canonical requests and JIT review material can still contain the exact provider URL or resource identifier required for approval and policy binding; those structures are trusted in-process authorization inputs, not diagnostic or audit fields. The erasure guarantee stops at gate-owned copies: reqwest, `url`, serde and parser internals, TLS, libc, the system allocator, and the kernel can allocate or retain additional copies that are contained by the measured process or future enclave but are not claimed to be individually erased. Current development Docker therefore does not prove enclave-only custody or allocator-wide zeroization.

## Authenticate The Operator

Development accepts the `dev-admin-token` through the portal token field. Production also supports bearer JWTs for automation and requires the built-in browser OIDC flow. Configure `SERVERWARE_OIDC_ENABLED=1`, `SERVERWARE_OIDC_BROWSER_LOGIN_ENABLED=1`, `SERVERWARE_OIDC_SESSION_WEBAUTHN_REQUIRED=1`, bounded pending/challenge/session TTLs, the issuer, audience, pinned JWKS, role claim, HTTPS authorization and token endpoints on the issuer origin, client ID, owner-only client-secret file, scopes including `openid`, and the exact `${SERVERWARE_PUBLIC_URL}/api/auth/oidc/callback` redirect. `ops/production-readiness.env.example` contains the complete variable set.

The portal **Sign in** button calls `GET /api/auth/oidc/start`. Serverware creates one-use state, a separate browser nonce, an OIDC nonce, and an S256 PKCE verifier/challenge. The encrypted verifier, OIDC nonce, and only the browser nonce digest are stored in the metadata store; the raw browser nonce is an `HttpOnly`/`SameSite=Lax` callback cookie. An allowlisted return target is bound server-side to that opaque state, so login can return only to `/`, `/approvals`, one exact `/approvals/{id}`, or `/?setup=<uuid>`; invalid targets normalize to `/`, and the callback never trusts a caller-supplied return value. The callback consumes the state once, exchanges the code with the verifier, validates the ID token against the pinned issuer/audience/JWKS/algorithm set and OIDC nonce, applies the configured subject and RBAC role claims, discards the raw token after hashing it, and sets a random opaque `HttpOnly`/`SameSite=Strict` cookie before returning to the state-bound target. In production this cookie is nonprivileged and expires within `SERVERWARE_OIDC_SESSION_WEBAUTHN_PENDING_TTL_SECONDS` unless the operator proves a currently trusted passkey.

The session challenge binds the OIDC subject, server-side session ID, pending expiry, final expiry, and a fresh nonce. Signature verification, challenge claim, authenticator-counter update, credential binding, trust-generation capture, token rotation, and activation commit atomically. The pending token is invalid after activation. Every privileged request rechecks session expiry, exact credential ownership/revocation, the current trust bundle digest/sequence and authenticator class, and authoritative RBAC. Passkey revocation atomically terminates all sessions bound to that credential. Unsafe API calls through pending or active cookies require the double-submit CSRF cookie and `X-Serverware-CSRF-Token` header. **Sign out** durably revokes the server-side session before clearing both cookies.

## Manage Operator Passkeys

The first portal band lists the current operator's active and revoked passkeys, effective authenticator class under the current trust bundle, attestation-root digest, last-use time, and retained revocation source. The API and bootstrap payload omit COSE public keys, development private material, and raw credential IDs. A pending OIDC subject with zero retained credential history can perform first enrollment using the production bootstrap token; sibling registration challenges are invalidated when the first key commits, and the new key must immediately prove possession before the session activates. **Register passkey** for every later key is a digest-bound control-plane mutation and can require a different operator's approval.

**Revoke** requires a non-empty reason, a fresh assertion over the exact credential record and reason, and the configured two-person approval. The row is soft-revoked rather than deleted; assertion lookup and sign-counter CAS exclude it, credential-ID reuse is rejected, and unconsumed JIT grants plus bound browser sessions are revoked in the same metadata transaction. Revoking the last active passkey intentionally does not reopen bootstrap. A pending OIDC login instead offers offline recovery. The portal creates the replacement credential locally, verifies its attestation, copies a canonical subject/session/history/trust/candidate-bound statement for an offline Ed25519 root to sign, and accepts only the signed exact statement. If the lost key remains active, the portal first requires a separate signed decommission statement for that exact active credential; the decommission signature cannot be reused for registration. Both ceremonies are short-lived, sequence/replay protected, atomically audited, and retain evidence. Recovery still leaves the session pending until the new key completes an ordinary assertion. Only the offline public key is mounted into Serverware; keep the private root on a separately operated signer. Production also requires the recovery witness PostgreSQL DSN to reach a different server address or port from metadata. A witnessed signature is burned even when the later metadata transaction fails, so the operator must sign a new statement rather than replaying old authority.

Production additionally requires different PostgreSQL `system_identifier` values and distinct operator-pinned metadata/witness fault-domain IDs; separate aliases or listeners on one cluster do not count as independence. Both database roles need permission to execute `pg_control_system()`. The witness claim occurs under the serialized metadata authority transaction before credential or sequence mutation, so parallel finalization has exactly one winner; a witness commit followed by metadata failure still burns the authorization and requires a fresh ceremony.

Publishing a signed trust bundle re-evaluates every active attested credential against the candidate roots, AAGUID restrictions, and class. Removed trust soft-revokes affected rows with source `trust-root-withdrawal`; an empty `roots` array withdraws all roots. That revocation also terminates bound browser sessions. Even without publication, privileged session lookup rechecks the current trust generation and fails closed on mismatch or trust-store failure. A later bundle may restore a root for new registrations, but it cannot reactivate historical rows. Production protects `webauthn.credential.revoke` and `webauthn.trust.publish` with hardware WebAuthn and two-person approval.

In the X developer portal, create the application, enable OAuth 2.0 user authentication, register the exact HTTPS callback above, and configure the scopes needed by the assigned templates. Serverware is a confidential web client when a client secret is configured; keep that secret only in the owner-readable file. The current primary references are X's [OAuth 2.0 Authorization Code Flow with PKCE](https://docs.x.com/fundamentals/authentication/oauth-2-0/authorization-code) and [user access token guide](https://docs.x.com/fundamentals/authentication/oauth-2-0/user-access-token).

Production secret files must be regular non-symlink files owned by the distroless control-plane UID `65532`, use mode `0400` or `0600`, and be readable to the privileged host preflight. Plaintext `SERVERWARE_*_OAUTH_CLIENT_SECRET` variables remain a local-development convenience and are rejected by production readiness.

The portal uses OAuth 2.0 Authorization Code with PKCE. The start endpoint requires an authenticated Serverware operator and runs credential-create WebAuthn mutation MFA before redirect when that control is enabled. Two-person authorization is deliberately deferred because the account does not exist in the provider response yet. OAuth state is server-side, one-use, TTL-bound, and size-bounded before it is written to disk. Each state stores only the SHA-256 digest of a separate browser nonce; the raw nonce is held in a state-specific `__Host-serverware-oauth-<state>` `Secure`, `HttpOnly`, `SameSite=Lax` cookie and must match at callback. Multiple provider flows can therefore finish out of order without overwriting each other's browser binding. A callback from another browser fails without consuming the legitimate state, while a matching provider-denial callback consumes it. When the caller supplies a durable `setupSessionId` and its current `setupRevision`, only that session's owner may start consent. Serverware stores the canonical setup ID in the one-use state, stores only the OAuth state digest in the setup ledger, and validates the owner, provider, phase, and state digest before accepting the callback. The setup ID is not sent to the provider and is not added to credential metadata.

The successful callback exchanges the code, fetches the account from Google's user-info endpoint or X's `/2/users/me`, and refuses to stage a credential when that identity lookup cannot be verified. If production two-person controls cover `credential.oauth.activate`, the callback envelope-encrypts the token as a pending credential instead of inserting it into the active credential table. Its bounded review binds the exact provider subject, display account, canonical granted scopes, credential name/type, expiry, metadata keys, X app ID when applicable, and a payload digest that also commits to the encrypted token source. No lease can reference this pending row. For a durable Setup flow, only this successful path binds the unique pending row or newly created credential generation to the same setup session, renders a success page, and returns the browser to `/?setup=<id>`. Provider denial and callback validation, exchange, or persistence failure are terminal for that callback and render a non-redirecting error page; they do not provide return-to-portal continuity.

Back in **Verified accounts awaiting activation**, only the original OAuth requester can select **Request approval and activate**. WebAuthn mutation MFA runs for the exact activation payload, a different authorized operator decides the `credential.oauth.activate` request in the control-plane approval queue, and the original requester retries with that approval ID. Activation atomically consumes the approval, moves the same encrypted envelope into the active credential table without rewriting token material, deletes the pending row, invalidates leases, and audits the exact-account evidence. A Setup-bound activation additionally requires the same setup ID and current CAS revision, then records the resulting credential ID and generation in that session. Self-approval, account/digest/resource/setup mismatch, expiry, replay, stale revision, or any changed state fails closed. When two-person activation is not configured, callback activation remains immediate for local development.

If the initial token response omits `scope`, Serverware follows OAuth semantics and binds the requested scopes; an explicit response may narrow but never expand them. Purpose-bound v3 generation metadata and, when authorized, one v3 secret set inside the v2 encrypted envelope are issued later on data-plane demand.

`provider_identity_verified` means the provider account lookup succeeded. Google's `provider_email_verified` and X's `provider_profile_verified` are separate facts; do not conflate an identified account with a provider-verified email or X profile badge. A Google email becomes the displayed/stored provider account label only when the user-info response says `email_verified: true`; otherwise Serverware uses the stable provider `sub` and does not present an unverified email as account identity.

Refresh does not repeat the provider identity lookup. It preserves the callback-verified subject/account metadata and requires the refreshed scope set to equal the stored canonical set; an explicit expansion or reduction fails closed, while an omitted refresh `scope` retains the existing binding. Provider account reassignment or identity drift therefore still requires reconnecting and re-verifying the account.

Before every authorization-code or refresh exchange, Serverware durably changes its reserved revocation row to `exchange_in_flight`. A transport timeout, undecodable success response, or process interruption can leave the provider's issuance result unknowable. The row is retained as `issuance_uncertain_unreported`, reported once to the audit chain as `credential.oauth_issuance_uncertain`, then remains visible under **Provider issuance requires review**. It contains provider, requester, source, timestamps, and the bounded error, but no token response. It is not retried as a token revocation because Serverware has no token to present.

Do not clear that warning merely because a retry succeeded. The requester or an admin must first revoke the Serverware app grant in the provider account, record an evidence note, and explicitly confirm provider-side revocation. `POST /api/oauth/issuance-uncertainties/{id}/resolve` is protected by the `credential.oauth.uncertain.resolve` WebAuthn mutation and production two-person action, atomically consumes the matching approval when required, deletes only an uncertainty-state row, and audits the resolution. Until then, the row consumes bounded revocation-work capacity so an unresolved provider-side grant cannot disappear silently.

Pending activation has an explicit provider-revocation lifecycle. Cancelling a pending connection, letting it expire, or denying its exact-account approval changes its terminal status to `cancelled`, `expired`, or `rejected` and marks revocation `pending`. Serverware then calls the configured Google or X revocation endpoint with the refresh token when present, otherwise the access token. Success audits `credential.oauth_pending.revoked` and deletes the staged token material. Failure audits `credential.oauth_pending.revocation_failed`, retains only the terminal encrypted row plus bounded `revocation_status: failed`/`revocation_error` metadata, and exposes **Retry provider revocation** to the requester or an admin. A terminal row cannot be activated while revocation is pending or failed.

Provider-aware revocation also applies after activation. `DELETE /api/credentials/{id}` takes the cross-process credential lock, marks a managed OAuth credential `revocation_pending`, and immediately excludes it from new control-plane reads, token refresh, lease issuance, and lease renewal. A Rust gate that already holds a valid recipient-bound lease may continue to use that in-memory copy until its monotonic expiry, no later than five seconds; there is not yet a signed revocation-tombstone push channel. Serverware deletes local encrypted material only after Google or X confirms revocation; failure leaves a visible `revocation_failed` record and **Retry disconnect** action. **Reconnect** binds the existing credential ID and version into OAuth state, requires the callback to prove the same provider subject and account, revokes mismatched or stale newly issued material, and rotates the existing record in place so route and policy references do not change.

Google revocation applies to the account/project grant rather than one local credential row. Before activating or staging a Google callback, Serverware serializes credential mutation and rejects another active or pending credential with the same OAuth client ID and provider subject. Legacy rows without a stored client ID collide conservatively. The `409` response identifies only the nonsecret conflicting assignment impact; newly issued duplicate material is revoked immediately or retained in the durable retry queue if provider revocation fails. This prevents two Serverware rows from pretending they can be disconnected independently, but it is not a general provider-side grant-family inventory outside this deployment.

The callback stores the OAuth client ID as `oauth_client_id` for Google and `x_app_id` for X. Route assignment replaces every catalog placeholder in `credentialBinding` with the callback-verified provider subject and client ID; X `adapter.config.appIds` is set to the same one-element client-ID list. Typed templates declare the least OAuth scopes needed by the admitted operations. The one-post-per-UTC-calendar-day template requires `tweet.write` in addition to its read/user/offline scopes, so a default read-only X credential is disabled in the selector until the operator reconnects with write consent. Its half-open day runs from 00:00 UTC through, but not including, the next 00:00 UTC, when the quota resets. A pre-midnight reservation that has not entered dispatch expires at that boundary and must be retried against the new day; an unknown result after dispatch remains charged conservatively. A credential from another provider, an OAuth credential without a verified subject or client ID, a scope-incomplete credential, or an incompatible injection shape is rejected before candidate creation.

Static credentials use the same identity discipline without pretending that Serverware verified the provider account. Their non-secret Metadata JSON must contain a canonical `provider`, an operator-declared stable `provider_subject`, and a typed `secret_class`. The fixed-template setup flow preselects the provider and required class but leaves a visible `replace-with-account-subject` sentinel; storing or assigning that sentinel is rejected. Common classes are `bearerToken`, `automationToken`, `basicPassword`, `customHeader`, `queryToken`, and `cookie`. Candidate admission requires the stored values, signed credential declaration, route binding, and injection mode to agree exactly. The credential lease releases these labels to the data plane but never includes refresh tokens, access tokens, passwords, or other credential material in metadata.

The current credential inventory assumes one administrative trust domain. Operators with the relevant credential-management roles can act on the shared credential set; credentials are not tenant-owned, and the API does not isolate credential visibility or mutation by tenant. Treat one deployment as one administrative security boundary until explicit tenant and credential-ownership enforcement exists.

## Setup And Verify

The first portal section consolidates the common operator path without weakening the underlying controls:

1. Select a restriction template, principal, compatible credential, route ID, and any JIT approvers.
2. Use **Connect credential** when the provider account is not connected. OAuth and exact-account activation still run through their dedicated, audited controls.
3. **Preview assignment**, inspect every signed diff and allow/deny dry-run, then **Stage** the exact candidate through the authenticated durable package and decision-gate handoff. Staging does not activate the candidate or send it proxy traffic.
4. **Generate enrollment** only after an eligible candidate has completed authority finalization, the selected principal is assigned to the active route, and that route references the selected credential. The packet pins the current active policy hash; **Verify server evidence** records the current credential version and requires matching post-enrollment gateway evidence.
5. Download the signed packet, copy the verifier command and packet-derived agent instructions, run the verifier on the agent host, exercise the allowed route, complete JIT when required, and select **Verify server evidence**.

The Setup ledger's table and storage operations support both SQLite and PostgreSQL; that backend-neutral statement applies to the ledger, not to every service involved in the workflow. `POST /api/setup/sessions` creates a bounded, expiring session owned by the authenticated operator. `GET /api/setup/sessions` returns resumable session summaries without evidence or transition events. `GET /api/setup/sessions/{id}` returns the selected session with its evidence and transition events. The claim, handoff, cancel, credential, canary, policy, enrollment, and verify endpoints advance only named phases and require the caller's current `expectedRevision`; a stale writer receives a conflict with the current revision. Handoff by the owner or an admin records a bounded current-assignee subject string. It does not verify at handoff that the subject exists, grant that subject a role, reserve the run exclusively, or transfer OAuth ownership. When that subject later calls the API, normal authentication, role checks, participant checks, phase checks, and revision checks are enforced then.

Backend Setup binding fields are immutable once written: the assignment commits to the principal, route ID, canonical SHA-256 digest of the exact reviewed route policy, credential ID and generation, signed policy hash, and assignment digest. The current-assignee field changes only through claim or handoff. While a run is still in `created`, the portal leaves form controls editable; if the edited template, principal, or route no longer matches that run, the next action may create a replacement run instead of rebinding the existing backend record. Candidate binding re-compiles and verifies the signed staged bundle. Activation re-reads the active policy and rejects route, credential, policy, or assignment drift. Enrollment binding checks the exact packet digest and hashes the verifier nonce before storage; raw OAuth tokens, PKCE verifiers, enrollment capabilities, WebAuthn assertions, credential values, and verifier nonces are not setup-ledger fields.

Each transition and its evidence digests is written to a bounded audit outbox in the same metadata transaction as the session update. The consumer uses the stable transition-event ID as the audit idempotency key, supports stale-claim takeover, and leaves terminal records unprunable until their transition events have reached the hash-chained audit log. Capacity exhaustion fails closed.

The three status pills are intentionally independent:

- **Configuration ready** means the active signed policy, principal, route, credential, verified OAuth subject/scopes, and access-token-only injection agree.
- **Gateway telemetry correlated** additionally requires the signed enrollment packet's exact one-use CA capability to have been consumed and complete post-enrollment audit records for the exact policy/principal/route/credential/version. The compatibility API field remains `runtimeVerified`, but the response classifies it as `authenticated-correlated-telemetry`, not independent execution attestation. The server derives enrollment consumption, activated-canary monitoring, pre-dispatch authorization, and correlated response validation from authoritative session, policy, canary, grant, and audit state; it does not accept browser claims for those facts. JIT routes require both the authoritative grant-store consumption record and the matching data-plane response record to agree on request, operation, flow, grant, and approval bindings. The data-plane producer currently authenticates with a scoped bearer and server-derived instance identity, so these records do not independently prove which measured code authored them, that the provider accepted the request, or that response bytes reached the agent socket. Final response proof, measured-key event authorship, and provider-specific receipts are separate evidence.
- **Hardware unverified** remains pending until an independently signed hardware receipt is submitted. Server self-claims are not independent attestation verification. The portal and Setup API now issue the session-bound challenge, validate and store the exact signed hardware-assurance/proxy-statement bytes, enforce fresh challenge and cross-session replay checks, and retain the accepted evidence through completion. The separately trusted hardware verifier and off-host final authority must use distinct configured keys and bind the exact assignment, session, challenge, artifacts, release identity, and current host. Fixture authorities exercise this contract locally; no real production hardware receipt or independently operated authority exists for this checkout.

The durable ledger, control-plane endpoints, receipt APIs, and inline first-screen workflow are implemented, including successful OAuth callback/pending-activation continuity and server-derived canary/runtime reconciliation. The portal creates and selects durable runs, includes the selected run in `?setup=<id>`, resumes it after the operator reauthenticates, records a bounded handoff subject, keeps committed backend bindings immutable, and advances preview and stage through revision-checked endpoints. Activation now follows the bound signed-readiness path: publish the exact decision-gate generation, activate it through custody, provision eligible external evidence, then execute durable authority prepare, inclusion, and finalize operations. The legacy activation endpoint is not used. A claim sets the current-assignee string to the authenticated caller but is not an exclusive work lock. The receipt chain can reach hardware-verified and audit-gated complete states only after an eligible active assignment exists. These are source contracts; production acceptance still requires independently operated candidate-evidence, enrollment, hardware, external-verifier, and final authorities to produce a real measured receipt chain on the target TEE deployment.

## Connect A Provider Credential

1. Open `http://localhost:3000` for local Docker or the production control-plane URL.
2. Use **Sign in** for production browser OIDC, or enter the local admin token/a bearer JWT when that authentication path is intended.
3. In **Connect Provider Credential**, choose `Google` or `X / Twitter`.
4. Keep the default scopes for common read-only use or enter stricter provider scopes.
5. Click **Connect with OAuth** and finish the provider consent screen.
6. When exact-account two-person controls are enabled, inspect the verified account in **Verified accounts awaiting activation**, request activation, have a different authorized operator approve the `credential.oauth.activate` item, then complete activation as the original requester.
7. Confirm that the active credential appears as `kind: oauth2`, shows the expected provider account, and reports a verified identity. Treat `identity unverified` as unusable and reconnect it.
8. If **Provider issuance requires review** appears, revoke Serverware in the provider's app/security console before using the confirmation control. Record evidence, complete the passkey and second-operator workflow, and verify the uncertainty leaves the queue.

The connection form shows the currently connected Google and X accounts beside the provider controls. This is the assignment inventory: operators can inspect provider identity, scope compatibility, expiry, reconnect/disconnect state, and pending activation without searching the complete credential table. Credential metadata remains available under an explicit disclosure instead of filling the default workspace with raw JSON.

OAuth credentials store token material as encrypted JSON in the control plane. Managed Google/X policies must use the canonical access-token injection:

```json
{"type": "bearer", "header": "Authorization", "field": "access_token"}
```

The broker and Python prototype project the secret to a new JSON object containing only `access_token` before any lease/cache handoff. The refresh token remains in the control-plane refresh path and cannot be selected by policy. Fieldless OAuth injection, `refresh_token`, another header/query target, a non-bearer type, malformed or duplicate JSON fields, an empty/non-string access token, and oversized token material all fail closed.

The evidence verifier deliberately distinguishes normalized gateway output from raw provider-shaped data:

- The Gmail response artifact is `serverware.gatewayNormalizedGmailMessages/v1`, not a raw `messages.list` response. It represents a bounded list whose message resources were hydrated by the gateway. Every `internalDateEpochMillis` is a canonical decimal epoch-millisecond string. `capturedAtEpochSeconds` is explicitly marked `captureTimeAuthenticated: false`.
- The X recent-search artifact retains the provider response shape. Its exact request must include `tweet.fields=created_at`, and every returned `created_at` must be canonical second-resolution RFC3339 UTC within the requested lookback window.
- Gmail capture time, the X capture time and post-counter events, and observed JIT challenge, approval, and retry times must fit one caller-supplied interval no longer than 3,600 seconds. The verifier checks consistency and ordering only; it does not authenticate those timestamps or the origin of any transcript.
- The local ES256 check uses the public key included in the evidence set. The manifest labels that key `evidence-supplied-public-key`, `selfAnchored: true`, and `registeredAuthenticatorOwnershipEstablished: false`; it does not establish a registered YubiKey, authenticator ownership, or operator identity.

The optional `verify-authenticated` mode adds a closed `serverware.onboardingEvidenceVerifierEnvelope/v1` around the exact v3 manifest digest. The caller must independently supply the expected ES256 public-key SPKI digest, verifier and signer IDs, exact manifest digest, validity bounds, current verification time, and a fresh challenge byte file. The signed statement binds those values and the challenge digest; it does not retroactively authenticate the v3 timestamps or make the underlying browser/provider/JIT actions challenge-bound. A stale transcript can still be placed in a fresh envelope unless those source artifacts separately commit to the verifier's challenge.

Challenge consumption uses a caller-selected, effective-user-owned mode-`0700` replay root and an existing private ledger directory:

```bash
serverware-evidence --root /immutable/evidence verify-authenticated \
  --manifest onboarding-evidence.json \
  --envelope onboarding-evidence-envelope.json \
  --verifier-challenge verifier-challenge.bin \
  --expected-manifest-sha256 sha256:<manifest-digest> \
  --trusted-public-key verifier-envelope-es256.pem \
  --trusted-public-key-sha256 sha256:<spki-digest> \
  --expected-verifier-id <verifier-id> \
  --expected-signer-id <signer-id> \
  --expected-valid-from-epoch-seconds <inclusive-start> \
  --expected-valid-until-epoch-seconds <exclusive-end> \
  --verifier-time-epoch-seconds <trusted-now> \
  --replay-root /private/verifier-state \
  --replay-directory challenge-ledger
```

This authenticates only the pinned signer's envelope over the exact supplied values. The tool does not establish key-pin provenance, trustworthy time, challenge issuance, source/build/server/execution/TEE authorship, portable ACL privacy, or durable rollback protection. Root directory chains are pinned only for the invocation; a caller or host that can switch, delete, restore, or roll back the replay root can defeat cross-invocation uniqueness. Production needs an independently controlled signer, trusted time and challenge issuance, immutable evidence inputs, and monotonic or externally witnessed replay state.

## Review JIT Approvals

When an agent's first real proxied request hits a route that requires human approval, the release authority validates its full canonical request, leaves no quota or grant reservation behind, atomically creates or reuses the exact pending approval, and returns `428 serverware_approval_required` with `approval_id`, `approval_url`, and retry timing. The non-mutating `/v1/decide` preview never creates approvals. The agent gives the operator the exact URL, waits, and retries only the identical request after approval. It never receives a grant token or credential.

The approval URL is an application path such as `/approvals/apr_...`; deployments resolve it against the configured Serverware public origin before showing it to the operator. Opening that URL authenticates the operator, loads only the named review document, focuses the review panel, and preserves the exact route in browser history. The deterministic browser test verifies the approval ID, route, package, request digest, operation digest, focus, and absence of horizontal overflow before capturing this view.

In the portal **Approvals** table, open **Review** before approving. The review panel is populated from `GET /api/approvals/{id}/review` and shows:

- principal and source identity;
- route, credential reference, credential version, and policy hash;
- method, stored target-URL commitment, normalized operation fields, and request body hash; Serverware also retains an encrypted review URL containing the path and only redacted or policy-safe query values, while the original sensitive query values are not recoverable from durable approval storage;
- redacted payload summary and risk flags such as WebAuthn requirement, hardware attestation requirement, current policy hash, credential-version binding, and one-use grant;
- previous similar approvals or denials;
- exact retry semantics, including the request digest, operation digest, grant TTL, max uses, and the fact that the agent receives no secret or token.

Opening review now issues a short-lived, one-use server-side receipt bound to the approver and SHA-256 digest of that exact redacted review document. WebAuthn options include the receipt ID, review digest, and receipt expiry in the signed challenge. The approval transaction requires and atomically consumes the same live receipt while creating the grant, so a direct API caller cannot approve without first retrieving the matching review and cannot replay a reviewed document after approval. Opening review is itself audited.

Responsive **Approve** and **Deny** controls sit directly beside the canonical review, rather than requiring the operator to return to the queue. **Deny** accepts an optional bounded reason. Stale-policy, expired, denied, approved, or otherwise consumed reviews block further action in the UI and API. Approval performs the configured WebAuthn ceremony over the exact review receipt; approval and denial append exact searchable audit records. The desktop and narrow-viewport browser journeys exercise both decisions with the development WebAuthn shim, not a physical authenticator.

The portal keeps **Approve** disabled until the matching review has been opened. If the active policy changed after the approval request was created, the review shows `policy_hash_not_current`, the portal keeps approval disabled, and the approval API returns `409` so the agent must issue a new request under the current policy. Approval still runs through the configured WebAuthn/YubiKey policy and creates a server-side one-use grant. The identical retry atomically reserves that grant together with every shared quota, advances the exact attempt to `dispatching` immediately before upstream contact, and commits or refunds it according to the bounded completion state. Denial can include an operator reason through the API, and denial records are searchable in audit.

## Teach Agents To Use Serverware

Agents do not need provider tokens, OAuth refresh tokens, npm tokens, or API keys. Give them only the proxy/CA setup and the upstream API task.

![Serverware agent enrollment flow](images/agent-enrollment-flow.svg)

Generate an enrollment packet from the portal:

1. Open `http://localhost:3000` or the production control-plane URL.
2. In **Agent Enrollment**, choose the policy principal that will run the agent.
3. Enter the Serverware proxy URL, proxy egress CIDR, namespace, CA mount path, and optional pod selector JSON. The control-plane origin is read-only and derived from `SERVERWARE_PUBLIC_URL`; a submitted mismatch is rejected.
4. Click **Generate enrollment**, then **Download** in the Agent Enrollment panel. In the separate **Credentials** section, click **Download + copy verifier command**. That action downloads the exact signed packet again and copies a fail-closed command that verifies that file before any CA installation step. The Setup and Verify flow exposes the same action beside **Generate enrollment** as **Copy verification command**.
5. Click **Copy agent instructions** to download the exact packet bytes and copy a fixed `serverware-enrollment` command containing the separately computed raw-file digest, expected principal, and expected nonce. The installed verifier authenticates that file and fresh attestation before emitting the packet's signed `agentHandoff.authenticatedInstructions`. The emitted handoff contains every required step in order, the proxy and CA environment, required CONNECT and provider headers, token identifier when proxy authorization is required, allowed upstream URLs, verified Kubernetes/`nftables` requirements, bodyless GET/HEAD canaries, non-executable write previews, and exact approval/error behavior. It never includes the proxy-authorization secret or a provider credential.

The current Coder lane is blocked before build until the sealed clean-room launcher and digest-bound browser/npm closure above exist. Do not treat future Coder output as an installable enrollment release or production evidence, and do not run the superseded consolidated clean-room commands as part of this workflow.

A later trusted release process must separately build the enrollment package from the repository-owned zero-dependency PEP 517 backend, close every binary dependency with `serverware_agent_trust/requirements.lock`, verify deterministic wheel and `RECORD` bytes, publish a complete `SHA256SUMS`, and authenticate that checksum-file digest through an independent release channel. The browser lane similarly needs separately sealed Chromium and npm inputs. Until those artifacts and authorities exist, there is no current clean-room install command to give an agent. Even after that work exists, checksum closure alone will not prove source or image provenance, independent execution, server identity, or TEE attestation.

The same packet can then be generated from the installed CLI for automation:

```bash
serverware-enrollment \
  --principal-id agent:mail-reader \
  --proxy-url http://serverware-proxy.internal:8080 \
  --proxy-egress-cidr 10.42.0.10/32 \
  --selector app=mail-reader
```

The portal generates a fresh 32-byte browser challenge and requests a five-minute packet. The server signs the packet digest, principal, challenge, validity window, policy hash, and runtime-manifest digest with the response key named by the packet's attestation pins. Do not use a packet after `expiresAtEpochMs` or if its `nonce` is not the challenge you requested.

The portal returns a signed packet but does not independently verify it or add `verificationReceipt`. Verify the downloaded file itself; do not run generation mode again and treat the newly generated packet as proof of the portal packet:

```bash
ENROLLMENT_PACKET=serverware-enrollment-agent-mail-reader.json
VERIFIED_ENROLLMENT_PACKET=serverware-enrollment-agent-mail-reader.verified.json
EXPECTED_PACKET_SHA256=sha256:<value-copied-from-the-portal-command>
EXPECTED_PRINCIPAL=agent:mail-reader
EXPECTED_NONCE=<value-copied-from-the-portal-command>
serverware-enrollment \
  --base https://serverware.example.com \
  --verify-packet "$ENROLLMENT_PACKET" \
  --expected-packet-sha256 "$EXPECTED_PACKET_SHA256" \
  --expected-principal "$EXPECTED_PRINCIPAL" \
  --expected-nonce "$EXPECTED_NONCE" \
  > "$VERIFIED_ENROLLMENT_PACKET"
```

Use the digest, principal, and nonce from the separately copied portal command; do not recompute the expected digest from a file you are trying to authenticate. This mode first checks the exact raw downloaded bytes against that precommit. The digest covers principal, proxy/control-plane URLs, egress CIDRs, selectors, CA location, and every attestation pin. It then reads the bounded JSON object with duplicate-key rejection, rejects any preexisting untrusted receipt, obtains `/attestation` using the expected packet nonce, verifies the nonce-bound quote and runtime digest, compares every measurement pin, checks packet validity and expiry, and verifies the Ed25519 packet signature. Only then does it emit the same packet fields with a new `verificationReceipt`. A substituted file, unexpected principal or nonce, failed check, stale packet, altered egress rule, duplicate key, oversized input, or existing receipt is a hard failure.

The signed packet also carries a closed `serverware.agentEnrollmentTooling/v1` contract. Before verification, the copied portal command requires:

```text
serverware-enrollment --version
serverware-enrollment 0.2.0
```

The command, distribution, version, version-check arguments, and expected output are all signed packet fields. Missing fields, extra fields, a different command or distribution, and any installed-version mismatch fail closed. This is a protocol-compatibility check after verifier bootstrap; it does not authenticate the executable that reports its own version. Authenticate the exact wheelhouse checksum through an independent release channel before installation, then use the signed packet contract to prevent a different installed CLI version from handling that packet.

After exact packet verification succeeds, install the CA through the scoped enrollment verifier:

```bash
serverware-attestation \
  --base https://serverware.example.com \
  --enrollment-packet "$VERIFIED_ENROLLMENT_PACKET" \
  --ca-out .tmp/serverware-ca.pem
install -D -m 0644 .tmp/serverware-ca.pem /etc/serverware/serverware-ca.pem
```

The copied portal commands perform these steps in order with shell error handling and default to the exact downloaded packet under `$HOME/Downloads`. They never request, embed, or transmit the Serverware admin token or any receipt-signing private key. The signed packet carries a policy-hash-bound, principal-bound, short-lived, one-use verifier capability whose URLs are relative to the configured control-plane origin; it can read only the pinned policy and download the CA once. Set `SERVERWARE_ENROLLMENT_PACKET` or `SERVERWARE_PACKET_PATH` when the browser saves downloads elsewhere. The CA verifier writes `.tmp/serverware-ca.pem`, and `agentHandoff.caInstall.command` installs that verified file at the configured destination. The packet enumerates every allowed route URL, not just the first path, and binds the exact proxy environment, required CONNECT/provider headers, machine-readable `requestHandling` rules, deny-by-default egress controls, canaries, write previews, and deterministic `agentHandoff.authenticatedInstructions`. The shorter `instructionsText` is only a bootstrap that refuses to run without a separately authenticated raw-file digest. Proxy-authorization secret material is deliberately absent and must be provisioned separately when `agentHandoff.proxyAuthorization.required` is true.

Setup enrollment-receipt signing is a separate trust-domain operation. Run `serverware-enrollment --sign-setup-receipt` only on the independently controlled verifier, after transferring the precommitted packet, live nonce-bound attestation evidence, and launcher-signed egress evidence to that verifier. The production v3 receipt binds the quote provider, exact quote and verified-claims digests, quote-verifier identity, assurance/debug/self-rooted state, evidence identity, and the exact agent network namespace. It also binds an installed deny-by-default firewall state plus successful allow canaries for every packet route and the packet's deny canary. Production signing rejects development, debug, self-rooted, incomplete-assurance, fixture-egress, or mismatched evidence; `--development-receipt-fixture` is explicit and its output is production-ineligible.

The CLI's local Ed25519 private-key option is a protocol and fixture adapter, not proof of production key custody. A production receipt authority belongs behind an independently operated KMS/HSM or equivalent signing service that releases signatures only after the same closed verifier checks. Its key must never be mounted in, copied to, or referenced by the agent image, VM, portal handoff command, or Serverware workload. This repository does not implement or demonstrate that KMS/HSM authority. Transfer only the signed receipt back to the operator for upload through the Setup workflow.

and CA environment (the example below is not a native-production transport):

export HTTPS_PROXY=http://serverware-proxy.internal:8080

For a principal with `identity.mtls`, the signed packet now retains its public
certificate selectors and requires an HTTPS proxy URL. The authenticated
instructions require a separately provisioned workload certificate/private key
and independently verified outer-proxy CA, distinct from the intercepted-provider
TLS settings. Environment variables alone are insufficient. See
[ordinary workload mTLS](workload-mtls.md) for the two TLS layers, an explicit
client configuration template and the remaining SDK/provisioning boundary.

This block is not the complete enrollment. Apply the packet's signed Kubernetes NetworkPolicy or recorded-namespace `nftables` deny-by-default egress controls and execute every applicable canary before starting the agent. For a principal that uses top-level `principals[].requiredHeaders`, HTTPS clients must also send those identity headers on the proxy `CONNECT` request and the provider request. For example, curl uses `--proxy-header 'X-Serverware-Agent: mail-reader'` for the tunnel and `-H 'X-Serverware-Agent: mail-reader'` inside it. The enrollment packet exposes these as both `agentHandoff.requiredProxyHeaders` and `agentHandoff.requiredProviderHeaders`; the former also contains the per-enrollment `X-Serverware-Enrollment-Session` value, which is sent on `CONNECT` but not repeated inside that tunnel. The packet separately exposes any `identity.proxyAuthorization` requirements, whose secret must be provisioned outside the packet. Production deployments should prefer source-bound proxy authorization or isolated source CIDRs when the agent SDK cannot set custom proxy headers.

Do not confuse principal identity headers with `generic.rest` `adapter.config.request.requiredHeaders`. Adapter-required headers are ordinary provider request fields that must also appear in `request.allowedHeaders`; they are checked after route/principal matching for bounded UTF-8 byte length and an optional safe anchored pattern, then forwarded upstream. They do not authenticate the `CONNECT` tunnel. The Stripe template uses this second mechanism for `Idempotency-Key`, so the agent must provide a fresh policy-conforming key on the provider request while separately satisfying its principal identity requirements.

Agent instruction block:

```text
Use the normal provider SDKs and upstream URLs.
Do not ask for, store, print, or cache provider credentials.
All HTTP and HTTPS traffic must use the configured Serverware proxy.
Apply the enrollment packet's proxy identity requirements to the proxy connection, including CONNECT.
If Serverware returns 428, give approval_url to the operator, honor retry_after_seconds, wait for human approval, and retry only the identical request.
If Serverware returns 403 or 5xx, stop and report the route/error; do not bypass the proxy.
```

The enrollment API serializes the packet once and returns those exact bytes with `X-Serverware-Enrollment-Packet-SHA256` on the authenticated portal response. The portal rejects a body/header mismatch, retains that response text verbatim, writes those same bytes to the download, and copies a fixed `serverware-enrollment --verify-packet ... --emit-verified-instructions` invocation with the server-supplied digest, principal, and nonce. It must not compute an expectation from an otherwise untrusted packet or copy either packet instruction field directly as authenticated text. Give the verifier output to the agent together with its separately provisioned proxy-authorization secret, when one is required. A new packet or policy assignment requires a fresh handoff; do not retain instructions whose packet has expired or whose pinned policy is no longer active.

Enforce egress so the agent cannot bypass Serverware. The enrollment packet includes a Kubernetes `NetworkPolicy` and an atomic `nftables` `inet` table scoped to the launcher-recorded agent network namespace. The installer verifies the exact table, output hook, drop policy, and signed rule markers after installation; any failure keeps the agent stopped and leaves an installed deny policy active. The dedicated table does not flush or replace unrelated firewall tables.

## Exact Credential Lease Flow

An enrolled agent never calls the secret broker. The Rust data plane uses two closed lease purposes after a signed route matches an exact `(policy hash, principal, route, credential)` scope:

1. Rust creates an ephemeral X25519 recipient key and one-use 32-byte nonce, then sends `serverware.credentialLeaseRequest/v3` with purpose `generationMetadata`, the scoped IDs, measured binary digest, requested TTL, and recipient-attestation evidence. Dispatch-only expected-generation and release-authorization fields are forbidden.
2. The control plane rechecks the active policy, principal-to-route assignment, route-to-credential assignment, provider/scopes, measured binary, nonce replay state, and recipient evidence. It reads one immutable credential snapshot without loading the master key, decrypting credential material, refreshing OAuth, or contacting the provider.
3. The signed and encrypted response retains the outer `serverware.credentialLeaseEnvelope/v2` cryptographic format, while its decrypted `serverware.credentialLeaseSet/v3` is purpose-bound and contains only credential version, an allowlisted metadata projection, and its digest. The generation entry structurally cannot contain `secret`. Cold policy scopes are not prefetched. Rust singleflights generation checks on a request or authorized preview, but only a successful authenticated non-preview request makes the exact scope hot for 30 seconds of bounded proactive refresh.
4. A credential-bearing JIT request uses that fresh generation to compute the canonical operation. The first unapproved request returns `428` without fetching a dispatch secret. Credential-bearing JIT is rejected when atomic release authorization is disabled.
5. After an approved identical retry atomically reserves the exact grant, quotas, request, operation, credential generation, and expiry, Rust sends purpose `dispatchSecret` as `serverware.credentialLeaseRequest/v4` with exact `serverware.credentialLeaseRequestAuthority/v1`, the reservation when one is required, and the expected version and metadata digest. A controlled operation with no separate durable reservation uses the closed `decisionBound` issuance kind. The control plane validates the live request-authority row and approver/WebAuthn authority, then atomically claims the only issuance for the exact attempt, request, recipient key, nonce, generation, policy, grant, approval, and expiry before decrypting or refreshing. It repeats authority and immutable-snapshot checks after encryption, and caps the lease to the authority expiry.
6. The controlled dispatch response is `serverware.credentialLeaseEnvelope/v3` containing `serverware.credentialLeaseSet/v4` and exactly one secret-bearing entry matching the generation and request authority. Managed Google/X material is projected to canonical JSON containing only `access_token`; OAuth refresh material never enters the data plane. Request v3, Envelope v2, and Set v3 are accepted only for authority-free uncontrolled dispatch. Purpose substitution, missing or extra secret material, version or metadata drift, stale policy, replay, and expired authority fail closed.
7. Rust enforces the five-second wall-clock and monotonic secret expiry through cache, injection, send-permit wait, and immediate pre-send validation. Non-JIT hot routes may renew their secret lease; JIT background work never schedules `dispatchSecret`. A response lost after the one-shot claim strands that claim and requires fresh approval rather than minting a replacement secret.

No plaintext lease file or plaintext credential-delivery response is part of this protocol. Development still uses a software recipient, so host root can inspect Rust memory; moving that recipient and unwrap boundary into a real enclave is production-host work.

The attested runtime manifest exposes this dispatch split as the closed `serverware.credentialLeaseCapability/v1` object rather than a single envelope-version string. Verifiers can therefore reject a controlled route that attempts the legacy tuple, require RequestAuthority v1 and the v4/v3/v4 request-envelope-set combination, and recognize `decisionBound` without treating legacy compatibility as general protocol support.

## Response Release And Audit

Credential injection does not imply that the upstream response is safe to return. Credential-bearing routes must use a bounded, projecting response mode; opaque `any`, non-redacting `stream`, and credential-bearing mutating request streams are rejected at policy admission.

- Success and error statuses use separate bounded profiles. Redirects are blocked, and a provider `4xx`/`5xx` without an explicit error profile is blocked.
- Only policy-selected safe semantic headers can be released. `Set-Cookie`, `Location`, authentication/session state, hop-by-hop headers, content encoding, and upstream content length are stripped and rebuilt.
- JSON fields, Gmail message-header names, body size, status, content type, and response date windows are validated before release.
- Before every credential-bearing upstream send, Rust synchronously submits `data_plane.credential.release_started` and requires the control plane to acknowledge its durable hash-chain append. Missing delivery configuration, transport failure, or ingest failure produces a local `503` and no upstream send.
- Immediately before send, Rust rechecks the active snapshot and exact lease version/expiry. Released body and safe-header values are scanned for configured credential representations; a match is blocked as `response_credential_reflection`.

The reflection guard is defense in depth, not general information-flow proof. A deliberately malicious approved provider could transform a secret into a value that also satisfies an allowed semantic field. Keep response projections narrow and do not treat an upstream service as trustworthy merely because its hostname is allowlisted.

## Attestation Checks

Before installing the CA or enabling production credentials, verify:

```bash
python3 scripts/verify_codebase_attestation.py \
  --base https://serverware.example.com \
  --admin-token-file "$SERVERWARE_ADMIN_TOKEN_FILE" \
  --release-signing-trusted-key /etc/serverware/trust/release-signing.pub.pem \
  --image-signing-trusted-key /etc/serverware/trust/image-signing.pub.pem
```

Pin the trusted release and image signing keys from an independently authenticated channel; keys downloaded from the server being verified are circular trust. In development this verifier checks internal consistency among the signed quote, runtime manifest, policy signature, policy high-water record, `serverware.sourceTree/v2` digest, release provenance, image-signature digest, CA SPKI, and a nonce-bound **control-plane** response signature. Source manifest v2 commits to path, type, normalized mode, file bytes, symlink targets, tracked deletions, all tracked inputs, and relevant untracked source/build/config inputs. It does not prove that the Rust proxy ran in a hardware TEE.

For a safe, buffered `GET`, `serverware-proof-client` can send a fresh proof nonce through the CONNECT TLS tunnel and write `serverware.proxyResponseProof/v3`; `HEAD` is rejected. The proof pairs a v2 external client capture with the Rust `serverware.proxyResponseStatement/v2`. Both bind the exact atomic authorization historically observed at upstream dispatch, including observation time and reservation expiry, grant/approval identity when present, credential version, request/operation/attempt/consumption identity, raw upstream status/body/policy-header digests, exact projected status/body/selected headers, policy, runtime manifest, measured binary, release, server instance, and TLS exporter. The gate sends a fresh nonce in the actual dispatch call and embeds its canonical request plus the signed control-plane response as `serverware.controlPlaneAuthorizationReceipt/v1`. That receipt carries the canonical authenticated release-dispatch response-header items in `response.response_headers`, captured from the actual response and checked against the v3 statement before embedding, so custody and offline verifiers can recompute the header count/digest. The internal dispatch contract carries no cookies or credential material; the gate rejects secret-bearing header names before constructing the receipt. Production verification independently pins that response-signing key and requires the embedded receipt to match the complete authority tuple and timing; no separately supplied receipt artifact is accepted. The inline statement makes no current-authorization or downstream-completion claim; the client demonstrates receipt by possessing the response and valid proof. This is a real end-to-end byte binding in the development stack, but its `vendor_tee` is explicitly `none-dev`/`development-fixture`.

Control-plane responses use digest-only `serverware.responseSignature/v3`. The statement authenticates the complete body and the digest/count of a bounded canonical header list reconstructed from the final response, while excluding only `X-Serverware-Response-*` proof fields and hop-by-hop transport fields. Header names are lowercase and sorted, repeated `Set-Cookie` values retain their order, values use canonical unpadded base64url in the digest preimage, and duplicate singleton fields fail closed. The ordered header array is not embedded in the statement or proof header, so OAuth session cookies and other response values are not duplicated into public proof metadata. Rust reconstructs the list from the response it actually received and requires both count and digest to match before accepting the control-plane response. Only the separate cookie-free release-dispatch receipt persists the already verified list as `response.response_headers` for custody/offline recomputation; OAuth and session responses do not.

The native launch chain is readiness-only: `serverware.productionReadinessLaunch/v3`, `serverware.launchAuthorizationRequest/v2`, `serverware.launchAuthorization/v2`, `serverware.bootstrapReceipt/v3`, and [completion proof v6](../schemas/completion-proof.v6.schema.json). Release orchestration requires a fresh successful systemd invocation receipt rather than a condition-skipped unit. ## Current Operational Limits

- Managed OAuth credentials refresh on lease demand shortly before access-token expiry, with strict token-type parsing, scope non-expansion, refresh-token rotation handling, version rotation, audit, and cross-process single flight. A missing/expired refresh token or provider failure fails closed. X refresh always retires the superseded access token and retires the old refresh token only when the provider actually rotates it; a non-rotating refresh token remains usable. X reconnect replaces the grant and therefore queues both superseded tokens. Google credentials must be disconnected and revoked before the account is connected again because Google revocation applies to the account/project grant.
- Exact-account two-person activation is implemented for OAuth callbacks when `credential.oauth.activate` is protected. Terminal pending connections and post-exchange failures retain encrypted provider-revocation work for bounded automatic retry. Active managed OAuth disconnect fails closed through `revocation_pending`/`revocation_failed`; exact-account in-place reconnect is available only for X after version and identity validation.
- Do not create sibling logical credentials for the same Google account under one OAuth project until Serverware has a first-class grant-family model; Google can revoke all project grants for that account together.
- A host/process failure in the narrow interval after provider issuance and before encrypted revocation material is attached cannot be made atomic with an external OAuth server. Production acceptance still needs measured exchange custody and explicit uncertain-issuance recovery.
- Staged candidates receive no traffic before activation. Active-policy baseline events and directly supplied audit rows are untrusted, zero-authority status inputs and cannot authorize a candidate. The authenticated durable candidate-shadow, generation-publication, decision-gate activation, and authority-finalization paths are implemented in source, while the legacy activation endpoint is disabled. Real measured fleet evidence, eligible external verification, a production activation, and post-activation denial canaries remain unproven.
- Source CIDRs, headers, and proxy tokens are implemented, but non-spoofable mTLS/SPIFFE workload identity remains future work.
- An approved agent can still misuse data that policy legitimately allows, and an approver can approve the wrong operation. Least-privilege provider scopes and careful review remain necessary.
- The proxy and host can observe destination and timing metadata. A compromised host can deny service even when a TEE protects keys.
- Streaming response proofs, real hardware quote/KMS Recipient execution, parent-host observation evidence, TEE vendor bugs, side channels, and incorrect PCR/release mappings remain part of the deployment threat model.
