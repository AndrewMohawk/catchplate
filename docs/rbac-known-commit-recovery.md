# Independent RBAC known-commit recovery

This source connects a new verifier process to the independently retained RBAC pending intent and the actual protected metadata commit. It is source-only, unbuilt, unexecuted and unprovisioned. It completes only a positively established committed transition; unchanged rows, absence, expiry, failure, timeout or a caller verdict do not establish a safe outcome. The [ordinary witness](rbac-independent-currentness.md) remains the currentness owner.

## Separate current permission

The additive `catchplate.rbacWitnessEnrollment/v2` retains the original nineteen fields and adds `recoveryPublicKeyBase64Url`. Its separately enrolled Ed25519 key must differ from both the enrollment root and the actual configuration/runtime root. It grants no permission merely by being present. The envelope is `catchplate.signedRbacWitnessEnrollment/v2`; its signature domain is the exact v2 payload schema plus NUL and canonical Python-ASCII payload bytes. V1 originals are unchanged and cannot select recovery.

`catchplate.rbacWitnessStartup/v2` has the original eight fields plus mandatory `recoveryAuthorization`. Explicit null selects normal currentness, still requiring live original enrollment and configuration membership. A signed `catchplate.signedRbacWitnessRecoveryAuthorization/v1` selects **recovery only**, and only in the genuinely launched verifier role. HTTP runtime, planner and executor refuse nonnull recovery selection. Fixed descriptor delivery and the actual signed launcher/role/attestation admission remain in force; no URL, DSN, trust key or success assertion comes from HTTP.

The authorization's closed eighteen-field payload binds `complete-known-commit`, a distinct recovery ID, the actual current source/configuration, original enrollment/database/deployment, exact intent/request/capability/plan, original before/after heads and exact committed receipt/result byte hashes. It has its own absolute interval of at most five minutes. Actual processing is at most thirty seconds, clipped to this grant and the originally admitted fresh role/attestation lifetime. `authority_rbac_recovery.sign_authorization` is an offline independent producer; no runtime owns its private key.

The old execution deadline is checked only as historical evidence that the actual committed receipt was within its original bounds. It is never replaced, extended or reused as permission to execute. Recovery can process a known commit after the old witness enrollment expired; that does not extend ordinary enrollment validity, TLS certificate validity, authorize another operation or admit another metadata cluster. Current verifier configuration may be freshly selected by the explicit recovery grant. The historical plan protocol/source must still be supported exactly; this is not an old-source adapter.

## Actual restart entrypoint and locks

Provision v2 initially with `authority_rbac_witness.provision` on the independently administered witness. It installs the existing five fixed procedures plus `recovery_head` and `recover_complete`, and immutable recovery-original association columns. V1 provisioning retains five procedures. Existing namespaces are refused: there is no automatic v1 upgrade, original replacement or head reset.

Launch the existing actual `verifier` role through its fixed descriptor/credential admission with the v2 cold startup original containing the recovery grant. `AuthorityProcess` admits the real current role and retained originals. `authority_service.main` detects this source-owned mode, calls `control_plane_rbac_recovery.run(process)` once, and exits **before creating the authority server/listener**. There is no new public resolver, token endpoint, callback validator or metadata execution call. Errors also exit; no retry loop exists.

The consumer first takes the external witness head's exclusive row lock. The actual normal executor holds a SHARE lock through its metadata commit, so recovery cannot cross an in-flight executor. Only then does recovery open its genuine verifier read-DSN transaction with TLS/role/current cluster checks, exact read-only ACL admission, REPEATABLE READ READ ONLY and bounded waits. It compares actual metadata roots to the independently expected after-head while retaining the witness lock. This lock order matches normal execution; it never calls a writer while holding a conflicting metadata lock.

Five purpose-used retained tables are added to the fixed verifier SELECT inventory: writer capabilities, planner transactions, execution envelopes, writer receipts and consumed envelopes. No runtime DML, metadata procedure execution, arbitrary table selector or new writer DSN is granted. Deployment must install the source ACL changes; missing privileges fail closed.

## Positive committed evidence and durable completion

The reader requires all five exact PK-bound rows. Capability and execution envelope must be committed, planner consumed, original v3 protocol unchanged and no failure fields present. It decodes the exact retained plan, request and result, checks byte counts/hashes and joins the plan hash to the independently retained pending intent. The plan was genuinely admitted before that intent was reserved; recovery does not pretend a re-run of the live, deadline-sensitive planner validator grants historical execution.

The actual v9 commit transaction already wrote the same terminal receipt to the planner and execution envelope, the result to the writer receipt, and matching consumed-envelope/capability transitions. Recovery checks those originals together, their domain-separated receipt/result digests, request/capability/planner/envelope/fence identities, original action deadlines, expected result and before/after root commitments. The fresh grant must select these exact receipt/result originals. No new outcome signature is invented.

Only then does the fixed witness procedure compare the original pending predecessor and store the exact ordinary completion original **plus the fresh signed recovery original, its hash and unique recovery ID** in the same transaction that advances the head and clears that pending digest. It does not delete the intent or execute metadata SQL. The owner reads back the exact completion, retained recovery original and head, and reports only after external COMMIT and its closing checks return. A matching already-completed record follows a read-only branch; it cannot repeat a metadata or completion effect.

The eight-field `catchplate.rbacWitnessRecoveryObservation/v1` has `okForAction:false` and either `recovered-known-commit` or `observed-complete`, with only original hashes. It is not a bearer permit or proof of future currentness. The [paired schema](../schemas/rbac-witness-recovery.v1.schema.json) is data-only.

## Uncertainty and remaining lifecycle work

Missing/rolled-back rows, conflicting receipts, a different current metadata root, failed/unknown execution or a changed cluster remain unresolved. No transition is abandoned on an absence test. A lost completion ACK ends that process without a retry; a separately admitted recovery process must repeat the actual known-outcome read, not the original metadata effect. Recovery does not reopen serving in that process. Subsequent normal processes recheck the actual completed independent head and must independently satisfy their ordinary live enrollment/configuration.

Grant originals are at most 16 KiB, startup 96 KiB, exact retained plan/request/result at most 8 MiB each and completion 8 MiB; larger originals fail rather than truncate. No record quota or historical capacity is reclaimed. V1 migration, unsupported historical sources, root/certificate/cluster handover, ordinary enrollment expiry, record exhaustion and positively authorized noncommit resolution remain required separate lifecycle work. Independent deployment, provisioning and runtime/crash/concurrency acceptance are not claimed.
