# Fixed guest custody role startup

This is a source-only fixed child entrypoint for the seven existing response-v2 services. It is not a secret provisioner, a new backend or quote, a host-UDS relay, a runnable EIF, or evidence that a guest cohort has started. The native parent factory must retain the actual children and original native lifetime; independently provisioned role seeds, signed delivery/generation, real TEE evidence, existing state directories and genuine durable backend remain required. Nothing here changes the host/systemd profile.

`serverware-response-v2-guest-role` has no arguments or environment. Its fixed inherited interface is paired by [the closed schema](../schemas/response-v2-guest-role.v1.schema.json): private parent seqpacket FD3; absent FD4; sealed root:root0600, zero-link bootstrap memfd FD5 (all four immutable seals, canonical UTF8 JSON, at most16KiB). Only the signed router receives the complete [listener6/7](response-v2-guest-listener.md) and [inspector8/9/10](response-v2-guest-inspector-router.md) handoff. Inherited originals cannot alias and are CLOEXEC before generation/TEE verifier children. Unrelated descriptors and stdio are closed; no command or incoming reply protocol exists.

The bootstrap's exact eight fields are `apiVersion`, `configurationPath`, `configurationSha256`, `deliveryPath`, `deliverySha256`, `serviceRole`, `gateLifetimeDeadlineBoottimeNs`, and `channelNonce`. The label is `serverware.responseV2.guestRoleBootstrap/v1`; the lifetime is a positive canonical u64 decimal string and the nonce is a nonzero canonical base64url32 original. Its unsigned sealed bytes are consistency, not independent role or boot authority. The real private parent endpoint must identify the actual root launch parent through SO_PEERCRED, SO_PEERPIDFD and getppid. The parent supplies its original native lifetime, never a refreshed startup allowance.

## Two-phase original custody

`guest_delivery::PreparedRoleDelivery::open` verifies actual root-owned config/delivery bytes, the independent config SHA, the distinct delivery authority signature, exact role/topology, generation, current boot and signed original startup window. Its parent-facing `scoped()` and digest/boot/deadline getters expose signed metadata only; no role credential or seed is read during root admission. The parent must compare its pinned fixed executable against every signed role's executable hash. The worker additionally hashes its actual `/proc/self/exe` (bounded64MiB) against its signed role before proceeding.

While still single-threaded, the worker arms a CLOCK_BOOTTIME absolute SIGKILL timer for the unchanged gate lifetime and irreversibly installs the signed real/effective/saved role UID/GID. It clears supplementary groups and all effective, permitted, inheritable, ambient and bounding capabilities; locks securebits; enables no-new-privileges and nondumpability; disallows core dumps. It reinstalls PDEATHSIG after credential changes and rechecks the original parent. Gate/router services gain neither CAP_SYS_PTRACE nor DAC privilege. The dedicated inspector remains a separate owner.

Only then does consuming `load_after_drop` read role-owned0400 generation/public/key originals, verify the real signed generation/TEE path, and check actual seed→public-key→assigned key-ID correspondence. Every cloned consumer receives the same private delivery Arc. This phase checks retained original FD bytes and stat identity instead of reopening root0400 configuration paths. It neither chmods/chowns history nor silently chooses a replacement path. Role credential paths must already be traversable/readable by the exact signed final role. Original possession is not current generation permission: the unchanged generation/backend/quote consumers still enforce their real authority and deadline checks.

The parent's distinct consuming `into_lifetime` transition is allowed only while root admission and original startup checks still hold. `RoleDeliveryOriginals` thereafter checks the same held config/envelope FDs, PID and boot, including after the gate's UID drop. It cannot load seeds, construct service config, renew time, or certify readiness. The parent performs this transition only after genuine child `started` progress and retains its independent native lifetime owner.

## Actual service and activation order

The required parent order avoids reading nonexistent dependency readiness:

1. Launch state-authority. The child always calls the existing signed generation bootstrap/reconciliation operation before starting its real service; it does not decide whether to bootstrap from absent files. The authenticated durable backend retains its existing install/reconciliation semantics.
2. Wait for state-authority `listening`, emitted only after the existing live service-readiness handshake. Its activation thread now publishes the real activation context and awaits all seven role artifacts, while that same process publishes its own artifact.
3. Launch the five other nonrouter services and await each `listening`. Their existing readiness constructors require state-authority's signed completed-reconciliation record.
4. Launch the router with the actual listener/inspector originals; its existing constructor requires all six dependency readiness records. Await all seven `started` notices.

Each passive notice is exact five fields: `apiVersion`=`serverware.responseV2.guestRoleStartup/v1`, `channelNonce`, `bootstrapSha256`, `serviceRole`, `phase` (`listening` then `started`). It is at most1024 canonical bytes, sent once on FD3. The parent must enable PASSCRED/PASSPIDFD and compare each actual final-role kernel sender with its retained original child PIDFD. Socketpair creator credentials or forwarded notice bytes are not final service identity.

For every role, `started` follows actual local generation-readiness artifact publication. State-authority sends it only after its concurrent activation operation has collected/verified all seven artifacts, committed the existing READY transition and obtained the existing signed backend result. The notice itself is still passive source-child progress, not a new signed generation assertion. All startup work remains under each original delivery deadline; neither thread creation, waiting, phase notices nor callback work renews it.

A parent/PIDFD/channel/lifetime monitor is installed before service threads. The absolute kernel timer and post-drop parent-death signal do not rely on the now-unprivileged parent being able to signal a distinct role UID. Failure of a service, activation or monitor terminates the whole child without retry. Long-lived serving retains original file custody and native lifetime; it does not turn the expired startup grant into a new generation or operation grant. No current generation, readiness record or historical file is deleted, reset, re-owned or fabricated by this delivery seam.

The [fixed native cohort factory](native-guest-cohort.md) connects this worker's signed originals, actual child/PIDFD ownership and ordered progress in source. Native cold-profile/lifetime selection, guest provisioning, real backend/TEE acceptance and full native release packaging remain open. No build, parser, test, runtime, cloud or provider execution was performed for this source checkpoint.
